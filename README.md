# Client Matcher

Веб-приложение для сопоставления идентификаторов одного человека в двух системах: CRM фонда и базе сайта. Сотрудник находит человека в CRM, указывает ID его записи на сайте, проверяет данные и сохраняет связь между двумя ID.

## Запуск

Для запуска нужны Docker Desktop или Docker Engine с Compose v2, Make и браузер. Устанавливать Go, Node.js и PostgreSQL на компьютер не требуется.

```bash
git clone https://github.com/437i/client-matcher.git
cd client-matcher
make run
```

Команда соберёт и запустит приложение, применит миграции, дождётся готовности веб-интерфейса и откроет его в браузере.

Адреса по умолчанию:

- **Приложение:** http://localhost:3000
- **Swagger UI:** http://localhost:8080/docs/

Если Make не установлен, приложение можно запустить напрямую:

```bash
docker compose up --build -d
```

В Windows запускайте `make run` из Git Bash или MSYS2, где установлен Make. Порты по умолчанию — `3000` (frontend) и `8080` (backend); изменить их и другие параметры можно в `.env`, созданном из `.env.example`. Порты доступны только с локального компьютера.

### Основные команды

| Команда | Действие |
|---|---|
| `make run` | Собрать и запустить приложение, открыть сайт |
| `make up` | Собрать и запустить приложение в фоне |
| `make down` | Остановить приложение, сохранив данные |
| `make ps` | Показать состояние контейнеров |
| `make logs` | Показать логи сервисов |
| `make verify` | Запустить тесты и проверки проекта* |
| `make reset-data` | Удалить базу данных и все сохранённые связи |

\* Для `make verify` дополнительно нужны Go, Node.js и npm. Команда `make reset-data` необратимо удаляет данные PostgreSQL.

## Как пользоваться

1. Найдите человека по имени или фамилии и выберите нужную запись CRM.
2. Введите известный ID записи сайта и загрузите её.
3. Сверьте данные обеих записей.
4. Сохраните связь. Она появится в списке ранее созданных соответствий.
5. Скачайте CSV со всеми сохранёнными связями.

## Данные и правила сопоставления

Для демонстрации используются синтетические CSV-файлы `testdata/crm.csv` и `testdata/site.csv` — они заменяют CRM и базу сайта. Сервер читает их в режиме только для чтения. Связи хранятся в PostgreSQL и сохраняются между перезапусками благодаря Docker volume.

Сервер оценивает выбранную пару по имени, фамилии и дате рождения. Статус `ready` означает, что проверяемые поля согласуются. При статусе `requires_confirmation` сотрудник может сохранить связь, если явно подтвердит расхождения и укажет причину. Если одной записи нет или один из ID уже связан, сохранить пару нельзя. Перед сохранением сервер повторно считывает обе записи и проверяет актуальность данных. Каждый CRM ID и каждый Site ID могут входить только в одну связь.

Экспорт содержит только два столбца в заданном порядке:

```csv
crm_id,site_id
```

Не добавляйте реальные данные, `.env` или секреты в Git. Собственная аутентификация и роли в приложении не реализуются. Production-развёртывание с реальными данными должно быть ограничено инфраструктурными механизмами, которые обеспечивает ответственная команда деплоя.

## Реализация

- **Backend:** Go, Gin; архитектура Ports & Adapters разделяет бизнес-логику, HTTP API и адаптеры источников данных.
- **Источники.** Для демонстрации используются CSV. Для сайта также доступен PostgreSQL-адаптер с отдельными настройками подключения. Интеграция с реальной CRM, включая Bitrix24, запланирована на следующий этап интеграции CRM.
- **Хранение:** PostgreSQL для связей, Goose для миграций.
- **Frontend:** React и TypeScript. Типы API генерируются из OpenAPI-контракта; проверка совпадения записей выполняется на backend.

Основные API-маршруты: `GET /api/v1/crm-clients`, `GET /api/v1/site-clients/{id}`, `POST /api/v1/links`, `GET /api/v1/links` и `GET /api/v1/links/export.csv`. Полная спецификация доступна в Swagger UI по адресу http://localhost:8080/docs/.

## Границы первой версии

При ручном подтверждении сервер сохраняет вместе со связью факт подтверждения, причину, время и структурированные коды расхождений. Общий журнал действий и идентификация сотрудника выходят за рамки первой версии, в которой нет собственных учётных записей и ролей. Редактирование и удаление связей и производственный мониторинг также выходят за рамки первой версии.

Для постоянного использования понадобятся возможность редактировать и удалять связи, журнал изменений, пагинация, резервное копирование и мониторинг. Ограничение доступа к production-развёртыванию с реальными данными обеспечивает ответственная команда деплоя.

## Проверки и использование ИИ

ИИ-инструменты использовались для анализа требований, обсуждения архитектуры, помощи с реализацией и тестами. Результаты сверялись с кодом и API-контрактом, затем проверялись автоматическими тестами и вручную на основном пользовательском сценарии. Конфиденциальные исходные файлы не передавались внешним ИИ-сервисам; для разработки использовались синтетические данные.

Проверки можно запустить командой `make verify`. Она выполняет тесты backend, проверки TypeScript, линтинг, тесты и production-сборку frontend, а также проверку конфигурации Docker Compose.

## Затраченное время

Трудно оценить даже примерно, делал несколько дней, когда появлялось свободное время. Субъективно оценил бы так:

- Анализ и проектирование: 1 час
- Backend и хранение данных: 4-5 часов, из них ~2 работал с код-агентом и ждал пока он отработает
- Frontend: ~4 часа работы с код-агентом, бо́льшую часть времени ждал

Можно было и быстрее сделать, но хотелось по максимум устранить ошибки в коде после его написания ИИ.

### Выбор источника сайта

При прямом запуске backend значение SITE_SOURCE по умолчанию — csv. В этом режиме
задайте SITE_PATH (например, ../testdata/site.csv из каталога backend).
Для обоих режимов задайте CRM_PATH и параметры собственной БД DB_*, примените
к ней Goose-миграции из backend/migrations, затем запустите go run ./cmd/server
из каталога backend. Стандартный Docker Compose запускает CSV-демонстрацию.

Для локальной проверки PostgreSQL создайте отдельную тестовую БД с синтетической
таблицей public.children (id BIGINT PRIMARY KEY, title VARCHAR, birthday TIMESTAMP).
Задайте SITE_SOURCE=postgres и отдельные SITE_DB_HOST, SITE_DB_PORT, SITE_DB_USER,
SITE_DB_PASSWORD, SITE_DB_NAME и SITE_DB_SSLMODE. Пример значений приведён
в .env.example. Выдайте пользователю сайта право SELECT на id, title и birthday.
Сервер остановится при ошибке подключения к выбранному источнику. /healthz
проверяет БД приложения.

Для обновления существующей БД связей остановите процессы записи, сделайте
резервную копию и проверьте восстановление. Goose отклонит обновление, если
существующие Site ID нельзя однозначно преобразовать в BIGINT. При откате
Goose вернёт каноничные десятичные строки. Исходное форматирование можно
восстановить из резервной копии. Production использует SITE_SOURCE=postgres
и новую пустую БД связей.
