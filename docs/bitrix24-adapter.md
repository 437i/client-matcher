# CRM-адаптер Bitrix24

Локальный режим CRM_SOURCE=csv используется по умолчанию и требует CRM_PATH. Стандартный Compose монтирует синтетический CSV только для чтения. Production Compose устанавливает CRM_SOURCE=bitrix24 и передаёт BITRIX24_WEBHOOK_URL только backend. Передайте полный URL из защищённого окружения или внешнего файла. Допустима классическая HTTPS-форма /rest/<user_id>/<secret>/ с положительным user_id, без параметров, фрагментов, userinfo и кодированных сегментов. Сбой Bitrix24 возвращается в действующем формате технической ошибки. CSV выбирается явно.

## REST и отображение полей

Смарт-процесс «Дети» имеет entityTypeId 135 и внутренний ID 6. B24GoSDK v0.2.0 отправляет JSON POST через классический REST. Классические crm.item.list и crm.item.get помечены deprecated. Оператор % позволяет искать подстроку и стоит в ключе фильтра. Переход на REST 3.0 требует проверки эквивалентного поиска. [SDK v0.2.0](https://github.com/bitrix24/b24gosdk/tree/v0.2.0) · [List](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html) · [Get](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-get.html)

| Поле REST | Значение |
| --- | --- |
| id | Канонический положительный int64 в виде строки в домене |
| title | SourceFullName, исходное полное ФИО |
| ufCrm7_1657182997586 | Фамилия |
| ufCrm7_1656048402 | Имя |
| ufCrm7_1656048409 | Отчество |
| ufCrm7_1656048422 | Календарная дата рождения |

Пример crm.item.list для одного токена.

~~~json
{
  "entityTypeId": 135,
  "select": ["id", "title", "ufCrm7_1657182997586", "ufCrm7_1656048402", "ufCrm7_1656048409", "ufCrm7_1656048422"],
  "order": {"id": "ASC"},
  "filter": {"0": {"logic": "OR", "0": {"%title": "иванов"}, "1": {"%ufCrm7_1657182997586": "иванов"}, "2": {"%ufCrm7_1656048402": "иванов"}, "3": {"%ufCrm7_1656048409": "иванов"}}}
}
~~~

Пример свежего crm.item.get для оценки или сохранения.

~~~json
{"entityTypeId": 135, "id": 42}
~~~

Get декодирует перечисленные поля из result.item и сверяет ID ответа. Неканонический ID запроса отклоняется до I/O. Отсутствующая или пустая дата даёт nil. Для RFC3339 сохраняется исходное YYYY-MM-DD. Некорректная карточка даёт ошибку данных источника. Неоднозначный NOT_FOUND, HTTP 404 и отказ в доступе дают техническую ошибку. Отмена и таймаут сохраняют действующую семантику. Ошибки и журналы содержат только безопасную классификацию.

## Поиск и оценка

Bitrix отбирает кандидатов по словам запроса. Фильтр дедуплицирует условия. Варианты известных имён используются для полей title и имени. Backend читает страницы до 50 строк через Core().Pages и локально ранжирует уникальные ID по Stage 0. При повторе сохраняется первая прочитанная версия. Лимит результата применяется после сортировки.

Предварительный локальный бюджет составляет 64 условия на фильтр, до 20 страниц по 50 записей на поиск и 12 секунд на всю операцию. На HTTP-попытку отведено 3 секунды, на вызов SDK — 4 секунды. MaxAttempts равен 1. Эти границы оставляют запас до 30-секундного HTTP WriteTimeout. При подтверждённом конце выборки чтение сразу завершается. Если после двадцатой страницы Bitrix сообщает о продолжении или начатая выборка прерывается из-за сбоя, поиск возвращает техническую ошибку без карточек, включая неполный top-50. Окончательная калибровка предела требует замеров на реальном портале после получения доступа. Распознанный next должен строго продвигать offset. SDK сводит отсутствующий, null и неразбираемый next к nil. Порядок по ID и дедупликация уменьшают влияние изменений данных между страницами, offset-пагинация допускает пропуски при изменении набора.

Опциональный дополнительный OR-фильтр ищет две части длинного слова при отсутствии положительных результатов основной выборки. Он использует общий бюджет и выключен в production до замеров на портале.

Заполненный title определяет отображаемое имя и слова для оценки. Исходные UF сохраняются независимо. При пустом title используются структурированные компоненты. Имя и фамилия сопоставляются по отдельным уникальным диапазонам целых слов. Одно дополнительное слово допустимо при подтверждении UF отчества или консервативным суффиксным правилом. Исходный title включается в fingerprint даже для CSV с пустым значением. Изменение форматирования title после оценки делает токен устаревшим.

При необъяснённом остатке CRM title сохраняются независимые доменные проверки, а аудит добавляет name:mismatch. В HTTP общая причина передаётся как last_name:mismatch с полными CRM и Site значениями. Stage 6 должен показать оба полных ФИО и описать причину как расхождение полного имени.

## Синтетический профиль Verify

В синтетическом наборе 25 121 запись. OR-фильтр для запроса «Иванов» суммарно возвращает 625 уникальных карточек. В каждой из них совпадающее значение помещено в одно из четырёх полей по ротации. При текущем бюджете 20 страниц выборка завершается за 13 вызовов, и поиск возвращает 50 ранжированных карточек. В таблице приведены исходные замеры Verify с бюджетами 12 и 13 страниц, по 20 повторов на сценарий. При бюджете 12 страниц поиск вернул ошибку без карточек.

| Сценарий | Страниц и попыток | p50 | p95 |
| --- | ---: | ---: | ---: |
| «Иванов», бюджет 12 | 12 за поиск | 225,54 мс | 228,35 мс |
| «Иванов», бюджет 13 | 13 за поиск | 247,67 мс | 249,19 мс |
| Опечатки, базовый фильтр | 80 за 80 поисков | 18,17 мс | 18,99 мс |
| Опечатки, дополнительный фильтр | 160 за 80 поисков | 55,98 мс | 57,06 мс |

На одних и тех же четырёх размеченных запросах базовый путь восстановил 0/4, дополнительный 3/4. Локальное декодирование и ранжирование 625 строк на Apple M1 заняло 4,96 мс за проход. В стенде тестовый сервер перебирает синтетический набор на каждую страницу. Замеры характеризуют этот стенд. Текущая верхняя граница — 20 попыток на поиск в пределах общего дедлайна и одна на GetByID.

## Чеклист разрешённой проверки портала

- Проверить scope crm и права пользователя webhook на смарт-процесс, каждый ключ select, четыре поля filter и сортировку по id.
- Проверить действие каждого условия с % и общей OR-группы, отсутствие незаметного расширения выборки, collation для регистра и ё/е, пустые UF и сортировку по ID.
- Проверить формат next, продвижение offset и завершение выборки, включая частую фамилию.
- Проверить квоты и задержки, затем подтвердить рабочие бюджеты и оценить целесообразность расширения для опечаток.
- Найти однозначный признак отсутствия именно карточки, отличимый от отсутствующего процесса и ошибки доступа.
- Проверить ingress access logs, включая Nginx и другие прокси, на отсутствие URL webhook, персональных данных и значения q. Диагностика production использует проверки состояния и config --services без вывода интерполированного окружения.
- Для сквозной проверки выделить отдельную чистую OD и применить штатные миграции. CSV и Bitrix24 используют разные пространства CRM ID.
