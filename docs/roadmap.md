# Client Matcher — контекст проекта и план дальнейшей разработки

Этот документ фиксирует назначение проекта, уже принятые решения, текущее состояние кода и последовательность дальнейшей реализации. Использовать его как исходный контекст при продолжении работы в новом чате.

## 1. Проект и цель

Репозиторий: https://github.com/437i/client-matcher

Основная рабочая ветка: `feat/crm-name-search`.

Исторический HEAD на момент составления плана (не текущий): `a01425d196bd3760961b11a3bc16597f7ee45a29`.

Стек:
- Backend: Go 1.26.1, Gin, pgx/v5, PostgreSQL, Goose.
- Frontend: React, TypeScript, Vite, TanStack Query.
- Архитектура: Hexagonal Architecture / Ports & Adapters.
- OpenSpec используется для проектирования и реализации существенных изменений.

Приложение предназначено для сопоставления записей одного ребёнка в двух независимых системах:

1. CRM фонда — в будущем Bitrix24.
2. Сайт фонда — PostgreSQL с таблицей `public.children`.

Собственная PostgreSQL приложения хранит связи между идентификаторами этих систем.

Главная задача приложения — помочь сотруднику найти правильные записи и связать их. Программа не должна самостоятельно решать, что две записи принадлежат одному человеку.

## 2. Принципиальные бизнес-правила

Эти правила обязательны для всей последующей реализации.

1. Поиск кандидата не означает установление личности.
2. Даже полное совпадение ФИО и даты рождения не гарантирует уникальность записи.
3. Дубликаты в CRM не объединяются и не удаляются автоматически.
4. Система показывает все подходящие записи, а окончательный выбор делает сотрудник.
5. Дата рождения участвует в оценке совпадения, но несовпадение даты не должно автоматически исключать кандидата.
6. Отсутствующая дата и отсутствующая часть ФИО — это недостаток информации, а не обязательно ошибка записи.
7. Любое существенное расхождение должно быть показано пользователю.
8. Связь с расхождениями можно создать после явного подтверждения и указания причины.
9. Отсутствие исходной записи или конфликт уникальности нельзя обходить ручным подтверждением.
10. Перед сохранением связи backend повторно получает актуальные записи и проверяет их.
11. CRM ID — `string`.
12. Site ID — первичный ключ `public.children.id` (`bigserial`). В Go он представлен как `int64`, в хранилище связей как `BIGINT`. HTTP JSON и path ID сохраняют строковый формат.

## 3. Текущее состояние

### 3.1. Что уже реализовано

В ветке `feat/crm-name-search` уже применён патч поиска CRM по ФИО.

Реализация находится в:
- `backend/internal/domain/client/name.go`;
- `backend/internal/domain/client/name_search.go`;
- `backend/internal/adapters/outbound/crm/csv/repo.go`.

Реализовано:

**Нормализация:**
- Unicode NFC;
- регистронезависимое сравнение;
- `ё` и `е`;
- нормализация пробелов;
- разделение слов по дефисам и другим разделителям.

**Поиск:**
- по любой части ФИО;
- порядок слов не важен;
- несколько слов запроса должны сопоставляться с разными словами кандидата;
- точные совпадения;
- префиксы;
- подстроки;
- ограниченное исправление опечаток;
- обработка смешения латиницы и кириллицы.

**Варианты имён:**

Начальный словарь:
- Ваня — Иван;
- Саша — Александр, Александра;
- Соня — Софья;
- Даша — Дарья;
- Настя — Анастасия;
- Маша — Мария;
- Тима — Тимофей;
- Лиза — Елизавета;
- Даня — Даниил;
- Варя — Варвара;
- Лёва — Лев;
- Петя — Пётр.

Варианты имён применяются только к компоненту имени кандидата, а не к фамилии или отчеству.

Исходные значения не изменяются. Нормализация используется исключительно для поиска и сравнения.

**Безопасность логирования:**

Gin настроен с `SkipQueryString`, а некорректные CSV-строки не должны приводить к записи исходных ФИО и дат в логи.

**Ограничения текущей реализации поиска:**
- Результат содержит упорядоченный список кандидатов, но не подробное объяснение каждого совпадения.
- Дата рождения пока не входит в критерии `CRMReader.Search`.
- Поиск выполняется по CSV в памяти.
- Нет отдельного локального поискового индекса CRM в PostgreSQL.

Не переписывать этот механизм заново. Сначала проверить его качество на расширенных синтетических данных и исправлять только обнаруженные дефекты.

### 3.2. Реализованная оценка и подтверждение связи

Stage 1 разделяет поиск кандидатов, оценку пары и сохранение связи. `ClientLinkService.Assess` повторно читает CRM- и Site-записи, проверяет занятость обоих идентификаторов, вычисляет структурированную оценку и выдаёт короткоживущий токен с версией правил и снимком данных. Перед сохранением сервис снова читает источники, проверяет токен и актуальность снимка, повторяет оценку и только затем создаёт связь.

Оценка возвращает статусы `ready`, `requires_confirmation` и `blocked`, проверки по полям и коды причин блокировки или расхождений. Статус `requires_confirmation` требует явного подтверждения сотрудника и причины. Отсутствие записи, занятый идентификатор, недействительный или просроченный токен и устаревшие данные блокируют сохранение. Уникальность пары дополнительно обеспечивает PostgreSQL.

Для подтверждённых расхождений сохраняется аудит факта подтверждения, причины, времени и структурированных кодов. Исходные ФИО и даты в аудит без необходимости не копируются.

### 3.3. Текущее хранение связей

Текущая таблица `client_links` содержит:
- UUID связи;
- `crm_id TEXT`;
- `site_id BIGINT`;
- `created_at TIMESTAMPTZ`.

Есть уникальные ограничения:
- один CRM ID может входить только в одну связь;
- один Site ID может входить только в одну связь.

Ограничения обеспечиваются самой PostgreSQL, поэтому конкурентные запросы не могут создать две связи с одним и тем же ID.

Это поведение необходимо сохранить.

На момент исходного плана Site ID был строковым в Go и `TEXT` в собственной БД. В Stage 2 добавлена Goose-миграция `site_id TEXT → BIGINT` с проверкой данных. Строковый HTTP-формат сохраняет точность за пределами диапазона JavaScript `number`.

### 4.2. База сайта

Пользователь предоставил фактическую схему таблицы:

Важные поля:

| Колонка | Тип | Особенность |
|---|---|---|
| id | bigserial | PRIMARY KEY |
| title | varchar | NULL допустим |
| birthday | timestamp | NULL допустим, без часового пояса |
| published | bool | NULL допустим |
| type | varchar | DEFAULT 'Child' |
| updated_at | timestamp(6) | NOT NULL |
| death_date | timestamp | NULL допустим |
| old | bool | NULL допустим |
| transfered | bool | NULL допустим |
| id_child_fond | varchar | NULL допустим |

- `id`;
- `title`;
- `birthday` после корректного преобразования.

### 4.3. Дата рождения в PostgreSQL сайта

Колонка имеет тип `timestamp without time zone`, то есть в ней хранится дата и время без информации о часовом поясе.

Для Stage 2 подтверждена трактовка сохранённого времени как UTC. Запрос приводит его к московской календарной дате.

```sql
SELECT id, title,
       ((birthday AT TIME ZONE 'UTC') AT TIME ZONE 'Europe/Moscow')::date AS birthday
FROM public.children
WHERE id = $1;
```

SQL NULL соответствует `Birthday == nil`. Поддерживаемая календарная дата представлена `client.Date`. Некорректная или неподдерживаемая дата возвращает ошибку источника. Интеграционные тесты на временной синтетической PostgreSQL проверяют NULL, переход дня около полуночи и неподдерживаемые даты.

## 5. Правила будущего сопоставления

Поиск и оценка пары — разные процессы.

### 5.1. Поиск кандидатов

Поиск отвечает на вопрос: какие записи стоит показать сотруднику?

Он не должен решать, можно ли создавать связь.

Для поиска:
- все части ФИО доступны для поиска;
- порядок слов не важен;
- отчество может отсутствовать;
- дефисы и составные имена должны учитываться;
- варианты имён дают дополнительные кандидаты с меньшим приоритетом;
- опечатки расширяют выдачу;
- дубликаты отображаются отдельно.

Дата рождения:
- не является жёстким фильтром;
- участвует в оценке пары;
- может использоваться как дополнительный фактор ранжирования, если она уже известна до поиска.

Если дата рождения отличается, кандидат не должен пропадать из результатов.

### 5.2. Оценка пары

Matching Service должен принимать две записи и возвращать структурированную оценку, а не только `error`.

Предлагаемые результаты:

**ready**
- доступные компоненты ФИО согласуются;
- различия объясняются безвредной нормализацией;
- даты совпадают, если они обе известны.

**requires_confirmation**
- применён вариант имени;
- есть вероятное, но не точное совпадение;
- дата отличается;
- дата отсутствует в одном из источников;
- есть существенное расхождение имени;
- недостаточно данных для уверенной оценки.

**blocked**
- запись отсутствует в источнике;
- ID некорректен;
- нарушается уникальность связей;
- другая техническая причина делает создание связи невозможным.

Не вводить проценты вида «95% — один человек». Использовать объяснимые признаки.

Пример структуры результата:

```json
{
  "status": "requires_confirmation",
  "checks": [
    {
      "field": "name",
      "status": "alias_match",
      "crm_value": "Александр Волков",
      "site_value": "Саша Волков"
    },
    {
      "field": "birthday",
      "status": "mismatch",
      "crm_value": "2020-12-15",
      "site_value": "2020-11-15"
    }
  ],
  "confirmation_required": true
}
```

Это только пример контракта, окончательные поля и статусы закрепить в OpenSpec.

Отсутствие отчества в записи сайта само по себе не является ошибкой: база сайта может содержать только имя и фамилию.

### 5.3. Создание связи с подтверждением

Нужен двухэтапный сценарий.

Первый запрос:

`POST /api/v1/link-assessments`

Получает CRM ID и Site ID, повторно загружает обе записи и возвращает подробную оценку.

Второй запрос:

`POST /api/v1/links`

Создаёт связь.

При отсутствии расхождений достаточно обычного подтверждения действия пользователем.

При расхождениях backend требует:
- явного подтверждения;
- причины ручного решения;
- актуального результата проверки.

Перед сохранением backend повторно получает записи и пересчитывает оценку.

Если данные изменились после предыдущей проверки, возвращает конфликт устаревшей оценки и требует повторной проверки.

Механизм передачи состояния оценки (например, короткоживущий assessment token или версия исходных данных) определить при проектировании OpenSpec. Не создавать сложную систему хранения промежуточных assessments без необходимости.

Ограничения:
- отсутствие записи — всегда блокировка;
- уже использованный CRM ID или Site ID — блокировка;
- уникальность 1:1 обеспечивает PostgreSQL;
- несоответствие ФИО или даты само по себе не позволяет создать связь без явного подтверждения.

Для подтверждённых расхождений сохранять:
- факт ручного подтверждения;
- причину;
- время;
- структурированные коды обнаруженных расхождений.

Полные исходные значения ФИО и даты не нужно копировать в журнал аудита без необходимости.

Аудит хранит факт, причину, время и коды ручного подтверждения. Собственная идентификация сотрудников исключена из плана.

### Этап 2. Site PostgreSQL Adapter

После готовности Matching Service.

Создать адаптер `SiteReader` для PostgreSQL сайта.

Он должен:
- получать запись по ID;
- читать только необходимые колонки;
- преобразовывать `birthday` в календарную дату;
- корректно обрабатывать NULL;
- не читать и не изменять ненужные данные;
- возвращать доменную модель, не раскрывая SQL в application/domain.

Сначала протестировать адаптер на локальной временной PostgreSQL с синтетической схемой `children`.

Использовать параметризованные запросы pgx.

Проверки используют только синтетическую PostgreSQL. Запрос использует подтверждённый ключ без дополнительных фильтров.

Готовность:
- адаптер проходит integration tests;
- оба источника используют порт SiteReader с ключом int64;
- новая миграция переводит site_id в BIGINT и сохраняет уникальность и аудит;

### Этап 3. SSH Tunnel Infrastructure

Stage 3 закрыт. Backend использует два независимых SSH-туннеля и PostgreSQL-пула для источника сайта (SITE) и собственной базы (OD). SSH использует TCP 22, PostgreSQL доступна как `localhost:5432` на стороне каждого SSH-сервера. Для SITE применяется пароль SSH, для OD — закрытый ключ без passphrase. Ключи SSH-серверов проверяются при первом подключении и восстановлении сессии.

В OD используется схема `apps`. Production backend применяет встроенные миграции Goose через OD-пул до открытия HTTP. Локальный Compose сохраняет прямое подключение, синтетические CSV и отдельный мигратор. При прямом запуске backend также доступен источник сайта PostgreSQL.

Параметры запуска приведены в [руководстве Stage 3](stage3-production.md), результаты Close и сверки решений Stage 0–2 со Stage 3 — в [PROJECT_STATUS.md](PROJECT_STATUS.md).

### Этап 4. Поисковый HTTP API

Подготовить backend-контракт для динамического поиска.

Сейчас существует:

`GET /api/v1/crm-clients?q=...`

В перспективе рекомендуется:

`POST /api/v1/crm-clients/search`

Пример:

```json
{
  "query": "артем семенов",
  "birthday": "2015-01-23"
}
```

Дата необязательная. Если она передана, её использовать как дополнительный фактор ранжирования, но не как исключающий фильтр.

Причины перехода:
- ФИО — потенциально чувствительная информация;
- GET помещает поисковую строку в URL;
- URL могут записывать reverse proxy и другие инфраструктурные компоненты.

Старый GET endpoint оставить на переходный период для совместимости с текущим frontend. Удалять его только после перевода frontend и согласованной проверки обратной совместимости.

Backend:
- принимает несколько слов;
- ограничивает количество результатов;
- поддерживает отмену контекста;
- не логирует ФИО;
- возвращает стабильный порядок кандидатов.

## 7. Архитектурные соглашения

Сохранять текущую Hexagonal Architecture:

`HTTP handler → Application service → Domain`

Ports определяются в `application/ports`.

Outbound adapters:
- CRM CSV;
- будущий CRM Bitrix;
- Site CSV;
- Site PostgreSQL;
- PostgreSQL Link Repository.

Domain не зависит от Gin, pgx, SQL, SSH или CSV.

Matching Service не должен знать, что CRM — Bitrix, а сайт — PostgreSQL.

Локальный Docker Compose сохраняется как development/demo-режим.

Не вводить Redis, Kafka, ORM, микросервисы или ненужные abstractions без конкретной причины.

Не менять внешний интерфейс или frontend ради удобства реализации backend.
