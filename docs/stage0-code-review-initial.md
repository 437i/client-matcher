## Findings

### Medium

**M1. `repo_dataset_test.go:56-75`, цикл по 55 site-запросам почти ничего не утверждает.**
- Сценарий: запрос по `title` из site-строки, затем проверяется только `len <= 50` и равенство двух одинаковых вызовов.
- Влияние: тест не отличит «кандидат найден» от «пустая выдача». Не проверяется, что у записи сайта есть ожидаемая CRM-пара или что пары нет (roadmap §8: «отсутствие потенциальной пары»). Сравнение двух вызовов на одном репозитории проходит для любого детерминированного кода.
- Исправление: для site-записей с известной парой добавить таблицу `site ID → ожидаемые CRM ID` и проверять вхождение. Минимум: `len(first) > 0` для строк с парой и явный список строк без пары.

**M2. `repo_dataset_test.go:72`, стабильность ранжирования не проверена на реальных данных.**
- Сценарий: сортировка уже детерминирована ключом, но порядок загрузки не варьируется. Перестановка строк CSV проверена только на 6 синтетических записях в `repo_stage0_test.go:25`.
- Влияние: пункт 10 roadmap («стабильность ранжирования») подтверждён частично. Регресс сортировки при равных score на полном наборе не будет пойман.
- Исправление: записать во временный файл `crm.csv` с обращённым порядком строк и сравнить выдачи по тем же запросам. Это дёшево.

### Low

**L1. `repo_dataset_test.go:121`, проверка `strings.Contains(c.FullName(), "Александр")` ничего не доказывает.**

- Комментарий на строке 112 («the known date discrepancy must not remove the selected search candidate») не соответствует коду. Реально это проверяет кейс «Саша Волков → 8680» выше, а блок со строки 113 лишь проверяет, что даты в фикстурах разные.
- Исправление: либо убрать tautology и переименовать блок («фикстура сохраняет расхождение дат»), либо запросить по site-имени «Саша Волков» и проверить, что 8680 найден при `Birthday` отличной от site 1066.

### Гипотезы (не подтверждены, дефектами не считаю)

- **H1. Внешний шлюз.** Headless-запуск идёт через `api.wellflow.dev` (по описанию в `agent-infrastructure-verification.md`). `AGENTS.md` запрещает отправлять пользовательские файлы во внешние сервисы. Для синтетического Stage 0 это допустимо по подтверждению пользователя, но для будущих review с реальными данными нужна явная проверка. Рекомендую одну строку в `agent-workflow.md`: «Review только синтетики; для реальных данных — не запускать».
- **H2. Auto Memory при `--print`.** Процедура сохраняет Auto Memory. Возможна запись фрагментов синтетических данных в память. Риск низкий, но это стоит отметить в документе.
- **H3. Сеть.** Первый headless-запуск в sandbox упал на ENOTFOUND, а процедура в `agent-workflow.md` не упоминает, что нужен выход в сеть. Это не дефект кода, а пробел в инструкции.
- **H4. Лимит 63 токена.** `MatchNameTokens` молча возвращает 0 при `len(candidate) > 63` (`name_search.go:142`). Для ФИО это нереалистично, но запись с таким ФИО станет невидимой без ошибки. Вне scope.
- **H5. Остаточные даты.** Реально расходящаяся дата в фикстурах подтверждена одна (Волков). Систематического аудита всех 55 site-записей на расхождение дат в тесте нет. Если в наборе есть и другие, они не зафиксированы.
