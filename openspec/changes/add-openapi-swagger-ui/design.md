# Design

## Context

Фактический контракт backend определён в `backend/internal/adapters/inbound/http/router.go` (6 маршрутов), HTTP DTO — в `handlers/dto.go`, единый формат ошибки и маппинг кодов — в `handlers/response.go`. Существующие тесты (`router_test.go`) фиксируют поведение этих маршрутов.

Ограничения, определившие решение:

- Go 1.26.1 (`backend/go.mod`), Gin 1.12.0, проект должен оставаться небольшим.
- Документация производна от кода: маршруты, статусы и JSON-поля менять нельзя, меняется только описание.
- В репозитории нет CI, Makefile и файлов документации API — генерация должна запускаться одной командой, а результат — коммититься.
- Спецификация и Swagger UI должны работать локально без CDN и без выхода в интернет.

Исследование инструментария (выполнено на временной копии проекта, вне репозитория):

| Инструмент | Результат проверки |
| --- | --- |
| `github.com/swaggo/swag/v2` v2.0.0-rc6 | Умеет `--v3.1`: на выходе настоящий OpenAPI 3.1.0 без остатков Swagger 2.0 (`schemes`/`host`/`basePath`). Требует Go ≥ 1.18 — совместим с Go 1.26.1 |
| `github.com/swaggo/swag` v1.16.6 | Только Swagger 2.0 — отклонён |
| `github.com/danielgtaylor/huma/v2` | OpenAPI 3.1, но требует переписать HTTP-слой на `huma.Register` — слишком инвазивно |
| `github.com/swaggest/swgui/v5emb` v1.8.9 | Swagger UI v5 с ассетами внутри модуля (`go:embed`), бандл содержит поддержку `openapi-3-1` |
| `github.com/getkin/kin-openapi` v0.153.0 | `openapi3.Loader` + `Validate` — проверка документа OpenAPI 3.1 в Go-тестах |

## Goals / Non-Goals

**Goals:**

- Спецификация OpenAPI 3.1, описывающая фактический контракт, хранится в репозитории и перегенерируется одной командой.
- Спецификация перечисляет все статусы, которые реально возвращают обработчики, включая нестандартный `499`.
- Backend отдаёт спецификацию и Swagger UI локально, без CDN и без внешних сервисов.
- Расхождение между описанием и реальными маршрутами и статусами ловится автоматическим тестом.
- Существующий HTTP-контракт, бизнес-логика, миграции и входные форматы не меняются.

**Non-Goals:**

- Генерация клиентов/SDK, генерация серверного кода из спецификации.
- Документация на уровне внутренних слоёв (Domain/Application/Repository).
- Аутентификация и авторизация маршрутов документации (сейчас авторизации нет вообще).
- CI-пайплайн, публикация спецификации во внешний реестр (например, Redocly Portal).

## Decisions

### 1. Генератор: `swaggo/swag` v2 с флагом `--v3.1`

Аннотации `swag` размещаются рядом с HTTP-обработчиками, спецификация генерируется из кода.

Почему: единственный инструмент, который даёт OpenAPI 3.1 из аннотаций в Go-коде без переписывания HTTP-слоя. Проверено на копии проекта: `openapi: 3.1.0`, `servers: [{url: "/"}]`, пути совпадают с реальными маршрутами, `uuid.UUID` и `time.Time` корректно схематизированы в `type: string`.

Альтернативы: swag v1 (только Swagger 2.0), Huma (OpenAPI 3.1, но требует переписать роутер), рукописная спецификация (нет воспроизводимой генерации, неизбежен дрейф).

Версия закреплена в команде генерации (`go run github.com/swaggo/swag/v2/cmd/swag@v2.0.0-rc6`), в `go.mod` генератор не добавляется — сборка и тесты не зависят от него.

### 2. Swagger UI: `github.com/swaggest/swgui/v5emb`

Статические ресурсы интерфейса лежат внутри модуля и встраиваются в бинарник; обращений к CDN нет. Swagger UI v5 понимает OpenAPI 3.1.

Альтернативы: `swaggo/files` + `gin-swagger` (Swagger UI 3.x, без поддержки OpenAPI 3.1), собственный `go:embed` с CDN-ресурсами (нужен интернет и своя поддержка ассетов).

Зависимость: `github.com/swaggest/swgui v1.8.9` + `github.com/vearutop/statigz` (indirect).

### 3. Спецификация встраивается в бинарник через `go:embed`

Новый пакет `backend/openapi` (публичный, вне `internal/`) содержит сгенерированные `swagger.json` и `swagger.yaml` и встраивает их через `//go:embed`. Роутер отдаёт эти байты как есть.

Почему: отдаваемый документ побайтово совпадает с файлом в репозитории (проверяется тестом), образ Docker не требует дополнительных файлов и томов, рантайм не зависит от генератора.

Альтернативы: `docs.go` от swag + `swag.ReadDoc()` (добавляет рантайм-зависимость на swag и дублирует спецификацию в Go-коде), чтение файла с диска (ломается в scratch-образе и требует монтирования).

### 4. Маршруты документации: `/openapi.json`, `/openapi.yaml`, `/docs`, `/docs/*`

Маршруты регистрируются вне `/api/v1` — рядом с `/healthz`, чтобы не смешивать документируемый API со служебными endpoints. Спецификация и UI не описывают сами себя.

`servers` в спецификации — относительный URL `/`: «Try it out» в Swagger UI обращается к тому же хосту, на котором открыт UI, поэтому префикс `/api/v1` не дублируется и не появляется прокси-специфичных адресов.

### 5. Проверка спецификации в тестах

`kin-openapi` загружает и валидирует документ; отдельная проверка сверяет пути и методы спецификации с `engine.Routes()` (служебные маршруты документации исключены); тест Swagger UI проверяет, что HTML не содержит ссылок на CDN и что статические ресурсы отдаются backend'ом.

Отдельный тест паритета (`openapi_parity_test.go`) поднимает настоящий роутер на заглушках источников и сверяет набор описанных в спецификации статусов с фактическими ответами обработчиков. Набор статусов выводится из общего мэппинга ошибок `handlers/response.go`: отменённый или превышенный по времени запрос даёт `499` и `504`, доменные ошибки — свои коды, всё остальное — `500`. Сценарии покрывают каждую операцию, поэтому расхождение фиксируется в обе стороны: и новый статус в коде без записи в спецификации, и задокументированный статус, который обработчик не возвращает.

Почему: без этого дрейф между описанием и кодом обнаруживается только вручную.

Альтернатива: только CLI-проверка при генерации (не защищает от рассинхронизации при последующих изменениях кода).

### 6. Ограничения генератора, которые принимаются

- `time.Time` и `uuid.UUID` схематизируются как `type: string` без `format` — форматы зафиксированы в комментариях к полям DTO (`YYYY-MM-DD`, RFC 3339). Альтернатива (теги `swaggertype` в DTO) отклонена: меняет структуру HTTP DTO ради документации.
- `swag v2 --v3.1` всегда пишет в корень документа объект `externalDocs` (даже пустой), а валидатор OpenAPI 3.1 требует непустой `url`. Поэтому в общую информацию добавлена аннотация `@externalDocs.url` со ссылкой на репозиторий проекта — иначе документ не проходит валидацию.
- Известные дефекты `swag v2 --v3.1` (например, пустые параметры для query-объектов и падение на именованных типах в query-объектах) в этом проекте не применимы: единственный query-параметр — строка `q`.

### 7. Типы содержимого ответов: порядок аннотаций вместо постобработки

`swag` применяет `@Produce` только к ответам, объявленным после него. Поэтому у операции `GET /api/v1/links/export.csv` ошибочные ответы объявлены **до** `@Produce text/csv`, а успешный — после:

```
//	@Failure		500	{object}	handlers.ErrorResponse
//	@Produce		text/csv
//	@Success		200	{string}	string
```

Результат: `200` — `text/csv`, ошибки — `application/json` со схемой `handlers.ErrorResponse`. Никакой постобработки артефактов не требуется, и поведение `swag` не приходится обходить строковой заменой.

Почему так: ошибочный `Content-Type` в спецификации вводит сгенерированные клиенты в заблуждение — они разбирают тело ошибки как CSV.

Альтернатива, отклонённая: отдельный шаг нормализации, переписывающий media type в готовом документе. Он зависел от точного текста, выдаваемого `swag`, и требовал синхронной правки двух файлов; при изменении формата генератора он портил артефакт вместо того, чтобы упасть с понятной ошибкой.

### 8. Публикация спецификации: промежуточный каталог и проверка до записи

`swag` пишет документы в `backend/openapi/.stage`. Второй шаг генерации (`publish_openapi.go`, файл с тегом `//go:build ignore`) читает оба файла, проверяет их и только потом публикует:

- JSON и YAML — валидные документы OpenAPI 3.1 (`openapi3.Loader` + `Validate`);
- типы содержимого соответствуют поведению обработчиков: у успешного ответа выгрузки CSV — `text/csv`, у остальных — `application/json`, а ошибки `/api/v1` ссылаются на схему `handlers.ErrorResponse`;
- JSON и YAML описывают одинаковый контракт (одинаковый набор операций, статусов, типов содержимого и ссылок на схемы);
- файлы публикуются атомарно: сначала записываются во временные файлы и переименовываются на место, при неудаче второго переименования первый возвращается к прежнему содержимому.

Гарантии шага:

- оба документа проверяются до записи — при ошибке файлы в репозитории остаются нетронутыми;
- шаг идемпотентен: повторный запуск на уже опубликованном документе ничего не меняет и завершается успешно;
- неожиданный media type, невалидный документ или расхождение JSON и YAML дают понятную ошибку с именем файла и найденным значением, а не тихую порчу артефакта.

Почему не оставили как есть: спецификация должна описывать фактический `Content-Type` ошибки, иначе сгенерированные клиенты неверно разбирают error-path.

Почему не ручная правка артефактов: `go generate ./openapi` должен оставаться единственной командой, воспроизводящей файлы (проверяется повторной генерацией).

Зависимость `github.com/getkin/kin-openapi`, которую использует шаг публикации, закреплена файлом `backend/openapi/tools.go` с тегом `tools`: `go mod tidy` не рассматривает файлы с тегом `ignore`, поэтому без `tools.go` требование могло бы исчезнуть из `go.mod`. Тег `tools` не включается при обычной сборке — в бинарник backend зависимость не попадает.

### 9. Полнота описания ошибок

Раньше аннотации перечисляли только «штатные» коды, поэтому спецификация не описывала два реальных ответа обработчиков: `502` (источник вернул клиента с пустой фамилией или некорректной датой рождения) и `499`/`504` (отмена запроса клиентом и истечение времени ожидания). Теперь аннотации перечисляют весь набор статусов из `handlers/response.go`, а тест паритета не даёт набору разойтись.

Код `499` нестандартный: `http.StatusText(499)` пуст, поэтому для него обязателен явный текст описания.

### 10. Swagger UI доступен только на чтение

Маршруты `/docs` и `/docs/*any` регистрируются методом `GET` и `HEAD`. Раньше использовался `engine.Any`, и интерфейс отвечал на `POST`, `PUT` и прочие методы, хотя ничего не меняет.

Почему: интерфейс только показывает спецификацию; лишние методы расширяют поверхность атаки без пользы.

## Risks / Trade-offs

- **`swag v2` — release candidate (v2.0.0-rc6)** → Версия закреплена в команде генерации, артефакты коммитятся в репозиторий, в тестах спецификация валидируется как OpenAPI 3.1. Следующее обновление версии выполняется отдельным изменением с перегенерацией и проверкой diff.
- **Генерация требует сети** (загрузка CLI в кэш модулей) → Сборка, запуск и тесты сети не требуют: артефакты уже в репозитории.
- **Дублирование контракта в аннотациях** → Расхождение путей/методов ловится тестом сверки с роутером, а расхождение по статусам — тестом паритета с поведением обработчиков; изменение полей DTO попадает в спецификацию при перегенерации, поэтому перегенерация выполняется в том же изменении, что и правка контракта.
- **Порядок аннотаций определяет тип содержимого** → Поведение `swag` зафиксировано экспериментально и закреплено тестом `TestSpecContentTypesMatchHandlers` и проверкой в шаге публикации: если `swag` изменит трактовку `@Produce`, генерация завершится ошибкой, а не тихо исказит media type.
- **Новые публичные маршруты `/docs` и `/openapi.json` раскрывают описание API** → В проекте сейчас нет аутентификации; при её появлении маршруты документации закрываются тем же middleware.
- **Swagger UI v5 встроен в бинарник (~1.5 МБ ассетов в сжатом виде)** → Размер образа растёт незначительно; альтернатива (CDN) запрещена требованиями.

## Migration Plan

1. Добавить аннотации, пакет `backend/openapi`, маршруты документации и тесты.
2. Выполнить генерацию, закоммитить `backend/openapi/swagger.json` и `backend/openapi/swagger.yaml`.
3. Собрать и запустить образ Docker — спецификация и UI доступны на тех же URL, что и раньше.

Миграции данных и обратная совместимость API не затрагиваются: добавлены только новые маршруты. Откат — удаление маршрутов документации и аннотаций; поведение API при этом не меняется.
