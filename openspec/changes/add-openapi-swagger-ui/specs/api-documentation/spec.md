# Spec Delta

## Purpose

Дать потребителям API машинно-читаемое описание фактического HTTP-контракта backend в формате OpenAPI 3.1 и локальный Swagger UI для ручной проверки эндпоинтов без внешних сервисов и без CDN.

## ADDED Requirements

### Requirement: Спецификация OpenAPI описывает фактические HTTP-маршруты
Система SHALL предоставлять спецификацию OpenAPI, в которой для каждого маршрута API указаны фактические HTTP-метод и путь, параметры запроса и пути, тело запроса, типы ответов и коды статусов, реально возвращаемые обработчиками. Схемы ответов SHALL соответствовать фактическим JSON-полям HTTP DTO, а не внутренним структурам домена.

#### Scenario: Поиск клиента CRM документирован
- **WHEN** потребитель смотрит спецификацию
- **THEN** для `GET /api/v1/crm-clients` указаны обязательный query-параметр `q`, успешный ответ `200` со списком клиентов CRM и ошибка `400` с общим форматом ошибки

#### Scenario: Выгрузка CSV документирована
- **WHEN** потребитель смотрит спецификацию
- **THEN** для `GET /api/v1/links/export.csv` указан успешный ответ `200` с типом содержимого `text/csv` и схемой строки с колонками `crm_id` и `site_id`

#### Scenario: Набор путей совпадает с роутером
- **WHEN** выполняется проверка согласованности спецификации и зарегистрированных маршрутов
- **THEN** пути и методы в спецификации совпадают с маршрутами приложения, кроме служебных маршрутов самой документации

### Requirement: Спецификация описывает все статусы, которые возвращают обработчики
Система SHALL перечислять для каждой операции все коды статусов, которые обработчик может вернуть, включая `502` (источник вернул некорректные данные клиента), `499` (запрос отменён клиентом) и `504` (превышено время ожидания). Набор описанных статусов SHALL совпадать с фактическим поведением обработчиков и проверяться автоматическим тестом.

#### Scenario: Ошибка источника данных документирована
- **WHEN** потребитель смотрит спецификацию операции `POST /api/v1/links`
- **THEN** среди описанных ответов есть `502` с общим форматом ошибки, а также `499` и `504` с описаниями отмены запроса и истечения времени ожидания

#### Scenario: Расхождение статусов обнаруживается
- **WHEN** обработчик начинает возвращать статус, которого нет в спецификации, либо спецификация описывает статус, который обработчик не возвращает
- **THEN** автоматический тест паритета завершается ошибкой, перечисляя расходящиеся статусы

### Requirement: Тип содержимого каждого ответа соответствует фактическому
Система SHALL указывать для каждого ответа фактический тип содержимого: успешный ответ выгрузки CSV — `text/csv`, все остальные ответы — `application/json`, а ошибки маршрутов `/api/v1` — со схемой общего формата ошибки `handlers.ErrorResponse`.

#### Scenario: Выгрузка CSV отдаёт разные типы содержимого
- **WHEN** потребитель смотрит спецификацию `GET /api/v1/links/export.csv`
- **THEN** у ответа `200` указан только тип `text/csv`, а у ошибочных ответов — только `application/json` со схемой `handlers.ErrorResponse`

### Requirement: Спецификация использует OpenAPI 3.1 и корректные servers
Система SHALL публиковать спецификацию в версии OpenAPI 3.1.x с валидным содержимым и SHALL указывать базовый адрес так, чтобы префикс `/api/v1` не дублировался в путях операций.

#### Scenario: Версия и базовый адрес
- **WHEN** загружается сгенерированная спецификация
- **THEN** поле `openapi` содержит версию `3.1.x`, а сервер описан относительным URL, не дублирующим `/api/v1` в путях операций

### Requirement: Backend отдаёт спецификацию по HTTP
Система SHALL отдавать сгенерированную спецификацию без внешних зависимостей по адресам `GET /openapi.json` (JSON) и `GET /openapi.yaml` (YAML), с корректным типом содержимого и с тем же содержимым, что и файл в репозитории.

#### Scenario: Получение JSON-спецификации
- **WHEN** выполняется запрос `GET /openapi.json`
- **THEN** возвращается статус `200`, тип содержимого `application/json`, а тело совпадает с сохранённой в репозитории спецификацией

#### Scenario: Получение YAML-спецификации
- **WHEN** выполняется запрос `GET /openapi.yaml`
- **THEN** возвращается статус `200`, тип содержимого `application/yaml`, а тело совпадает с сохранённой в репозитории YAML-версией спецификации

### Requirement: Swagger UI работает локально
Система SHALL отдавать Swagger UI по адресу `GET /docs/` (и `GET /docs`) вместе со всеми статическими ресурсами интерфейса, без обращений к CDN и без обязательного доступа в интернет, и SHALL настраивать интерфейс на загрузку спецификации с собственного backend.

#### Scenario: Открытие интерфейса
- **WHEN** выполняется запрос `GET /docs/`
- **THEN** возвращается статус `200` и HTML-страница Swagger UI, в которой указан локальный адрес спецификации и отсутствуют ссылки на внешние CDN

#### Scenario: Загрузка статических ресурсов
- **WHEN** браузер запрашивает ресурс интерфейса, например `GET /docs/swagger-ui.css`
- **THEN** ресурс отдаётся самим backend со статусом `200`

#### Scenario: Интерфейс доступен только на чтение
- **WHEN** выполняется запрос `POST /docs`, `PUT /docs` или `DELETE /docs`
- **THEN** возвращается статус `404`, а на `GET /docs` и `HEAD /docs` возвращается `200`

### Requirement: Генерация спецификации воспроизводима и артефакты хранятся в репозитории
Система SHALL генерировать спецификацию одной документированной командой из исходного кода, SHALL хранить сгенерированные JSON и YAML в репозитории и SHALL давать одинаковый результат при повторной генерации.

#### Scenario: Повторная генерация не меняет артефакты
- **WHEN** команда генерации выполняется дважды подряд без изменения кода
- **THEN** второе выполнение не создаёт изменений в сгенерированных файлах

#### Scenario: Артефакты доступны без генератора
- **WHEN** репозиторий используется без установки генератора
- **THEN** сгенерированные JSON и YAML спецификации присутствуют в репозитории и используются при сборке и запуске

#### Scenario: Некорректный документ не публикуется
- **WHEN** сгенерированный документ не проходит проверку (невалидный OpenAPI 3.1, неожиданный тип содержимого, ссылка на другую схему ошибки или расхождение JSON и YAML)
- **THEN** генерация завершается ошибкой, а файлы спецификации в репозитории остаются нетронутыми

### Requirement: Спецификация проверяется автоматически
Система SHALL проверять в автоматических тестах, что спецификация является корректным документом OpenAPI 3.1, что её пути совпадают с зарегистрированными маршрутами, что её статусы совпадают с фактическими ответами обработчиков, и что Swagger UI отдаётся локально.

#### Scenario: Валидация документа OpenAPI
- **WHEN** выполняется запуск тестов
- **THEN** проверка загрузки и валидации спецификации завершается успешно для версии OpenAPI 3.1

#### Scenario: Проверка соответствия поведению
- **WHEN** выполняется запуск тестов
- **THEN** сверка набора описанных статусов с фактическими ответами обработчиков завершается успешно для всех операций
