# Proposal

## Why

Backend не имеет машинно-читаемого описания HTTP-контракта: единственный источник правды — код роутера и handlers. Это мешает фронтенду и интеграторам (нужен ручной пересказ маршрутов), затрудняет ручную проверку эндпоинтов и делает регрессии контракта незаметными. Нужен OpenAPI 3.1, сгенерированный из фактического кода, и локальный Swagger UI, который работает без CDN и без внешних сервисов.

## What Changes

- В HTTP handlers добавляются аннотации `swag` (OpenAPI 3.1), описывающие фактические маршруты, параметры, тела запросов, статусы и ошибки. Поведение API не меняется.
- Спецификация описывает полный набор статусов, которые реально возвращают обработчики, включая `502` (источник вернул некорректные данные клиента), `499` (запрос отменён клиентом) и `504` (превышено время ожидания); у выгрузки CSV успешный ответ помечен `text/csv`, а ошибки — `application/json` со схемой `handlers.ErrorResponse`.
- В репозиторий добавляется сгенерированная спецификация `backend/openapi/swagger.json` и `backend/openapi/swagger.yaml` (OpenAPI 3.1), обновляемая одной документированной командой. Публикация атомарна: документы сначала проверяются в промежуточном каталоге и только потом попадают в репозиторий.
- Backend начинает отдавать спецификацию (`GET /openapi.json`, `GET /openapi.yaml`) и Swagger UI (`GET /docs/`) с локальными статическими ресурсами, без обращений к CDN. Интерфейс доступен только на чтение: `GET` и `HEAD`, без регистрации прочих методов.
- Появляются тесты, которые проверяют, что спецификация валидна как OpenAPI 3.1, что её пути совпадают с реально зарегистрированными маршрутами Gin, что набор описанных статусов совпадает с фактическими ответами обработчиков, а Swagger UI отдаётся локально.
- Новые зависимости: `github.com/swaggest/swgui` (Swagger UI v5, встраиваемые ассеты) и `github.com/getkin/kin-openapi` (валидация документа в тестах и в шаге публикации спецификации). Генератор `github.com/swaggo/swag/v2` в `go.mod` не добавляется: CLI запускается через `go run ...@v2.0.0-rc6`.

Вне рамок изменения: изменение самих HTTP-эндпоинтов, JSON-полей, статусов и бизнес-логики; генерация клиентов/SDK; интеграция с CI; документация на других языках.

## Capabilities

### New Capabilities

- `api-documentation`: машинно-читаемое описание HTTP-контракта backend (OpenAPI 3.1, сгенерированное из кода, хранится в репозитории) и локальный Swagger UI, который работает без внешних сервисов.

### Modified Capabilities

- Нет: существующих capability-спецификаций в проекте пока нет, а поведение API не меняется.

## Impact

- Код: `backend/internal/adapters/inbound/http/handlers/*.go` (только аннотации и комментарии), новый пакет `backend/openapi` (встроенная спецификация, генерация и шаг публикации), новый файл `backend/internal/adapters/inbound/http/docs.go` (маршруты `/openapi.json`, `/openapi.yaml`, `/docs/`), регистрация маршрутов в `backend/internal/adapters/inbound/http/router.go`, тесты в `backend/internal/adapters/inbound/http/`.
- Зависимости: `github.com/swaggest/swgui v1.8.9` (+ `github.com/vearutop/statigz` как indirect), `github.com/getkin/kin-openapi v0.153.0` (тесты и шаг публикации спецификации; в бинарник backend не попадает).
- Артефакты: `backend/openapi/swagger.json`, `backend/openapi/swagger.yaml` — коммитятся в репозиторий и встраиваются в бинарник через `go:embed`.
- Docker: образ собирается как раньше; спецификация и Swagger UI попадают внутрь бинарника, дополнительных томов и переменных окружения не требуется.
- Новые публичные маршруты: `GET /openapi.json`, `GET /openapi.yaml`, `GET /docs` и `GET /docs/*` — они не входят в `/api/v1` и не меняют существующий контракт.
