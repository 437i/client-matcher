# Design

## Context

Фактический HTTP-контракт backend зафиксирован в трёх местах и не меняется этим изменением:

- маршруты — `backend/internal/adapters/inbound/http/router.go:23-37`: `GET /healthz`, `GET /api/v1/crm-clients`, `GET /api/v1/site-clients/:id`, `POST /api/v1/links`, `GET /api/v1/links`, `GET /api/v1/links/export.csv`;
- HTTP DTO — `backend/internal/adapters/inbound/http/handlers/dto.go`: `CRMClientResponse` (`id`, `full_name`, `last_name`, `first_name`, `patronymic?`, `birthday` в формате `YYYY-MM-DD`, `clinic`), `SiteClientResponse` (`id`, `short_name`, `last_name`, `birthday`), `LinkResponse` (`id` UUID, `crm_id`, `site_id`, `created_at` RFC 3339), `CreateRequest` (`crm_id`, `site_id`), `ErrorResponse` (`code`, `message`);
- единый формат ошибки и коды — `backend/internal/adapters/inbound/http/handlers/response.go:33-63`: `query_empty`, `invalid_query`, `id_empty`, `invalid_body` (400), `crm_client_not_found`, `site_client_not_found`, `link_not_found` (404), `crm_already_linked`, `site_already_linked` (409), `last_name_mismatch`, `birthday_mismatch` (422), `internal_error` (500), `invalid_source_client_data` (502), `request_canceled` (499), `timeout` (504). Фактические коды и статусы сверены с `backend/internal/adapters/inbound/http/router_test.go:140-289` — этот тест фиксирует поведение, а не пересказ документации.
- состав полей записей: CRM отдаёт `id`, `full_name`, `last_name`, `first_name`, `patronymic` (необязательное), `birthday`, `clinic` (`handlers/dto.go:24-32`); запись сайта отдаёт `id`, `short_name`, `last_name`, `birthday` (`handlers/dto.go:34-39`). У записи сайта поля полного имени нет: `short_name` — первое слово названия записи на сайте (имя), `last_name` — остальные слова (фамилия), см. `backend/internal/adapters/outbound/site/csv/repo.go:67-75`.
- ограничения уникальности связей: `crm_id` и `site_id` уникальны по отдельности (`backend/internal/adapters/outbound/link/postgres/repo.go:26-29`), поэтому конфликт означает, что идентификатор занят **другой** парой, а не что текущая пара уже сохранена. Backend не сообщает, какая именно пара заняла идентификатор, — единственный способ узнать существующую пару для сотрудника это посмотреть список сохранённых связей `GET /api/v1/links`.

Тот же контракт машинно-читаем: `backend/openapi/swagger.yaml` (OpenAPI 3.1, `servers: [{url: "/"}]`), в репозитории и встроен в бинарник backend.

Ограничения, определившие решение:

- папки `frontend/` в репозитории ещё нет — это первый фронтенд в проекте, соглашения задаются этим изменением;
- backend вызывает `engine.SetTrustedProxies(nil)` (`router.go:19`) — за обратным прокси заголовки `X-Forwarded-*` не считаются доверенными, CORS-заголовки в backend отсутствуют;
- поиск по CRM ограничен 50 записями (`application/services/client_search.go:14`), пустой запрос даёт `400 query_empty`;
- проверка совпадения фамилии и даты рождения выполняется только на сервере (`domain/matcher/matcher.go`), связь 1:1 (уникальность на `crm_id` и `site_id`);
- правила `rules/frontend.md` и `rules/non-technical-ux.md` — обязательные продуктовые требования, а не рекомендации;
- данных клиентов в репозитории нет: `data/` исключён из Git, `testdata/` содержит синтетические фикстуры, которые читать нельзя.

## Goals / Non-Goals

**Goals:**

- один экран, который ведёт сотрудника фонда от поиска человека до сохранения связи и выгрузки CSV, без обучения и чтения технической инструкции;
- типизированный клиент, выведенный из репозиторной спецификации, без ручных DTO и без копирования правил сопоставления в браузер;
- состояния интерфейса, спроектированные заранее: начальное, загрузка, результат, пусто, ошибка, конфликт, успех, недоступная кнопка;
- доступность, позволяющая пройти весь сценарий с клавиатуры, с видимым фокусом и целевым размером элементов;
- воспроизводимая сборка и запуск через Docker Compose рядом с существующим backend, без правок backend.

**Non-Goals:**

- любая бизнес-логика во фронтенде, включая предварительную проверку фамилии и даты рождения;
- аутентификация, авторизация, роли пользователей, аудит действий;
- клиентский роутинг, страницы, вкладки, deep-link, SSR;
- глобальные стейт-менеджеры (Redux/Zustand), библиотеки форм, i18n-фреймворки, чарты, таблицы с сортировкой и фильтрами;
- офлайн-режим, кэширование ответов на диске, оптимистичные обновления;
- мобильное приложение, push-уведомления;
- реальное тестирование с сотрудниками фонда.

Node.js: локально 26.13.1. Минимальная версия для всего проекта — **`^22.22.2 || ^24.15.0 || >=26.0.0`**, и её задаёт `jsdom@31` (тестовое окружение); `vite@8` сам по себе допускает `^20.19.0 || >=22.12.0`, `vitest@5` — `^22.12.0 || ^24.0.0 || >=26.0.0`. В образе сборки используется `node:24-alpine`: актуальная ветка 24 — 24.22.3, она входит в диапазон `^24.15.0`. Диапазон фиксируется в поле `engines` файла `package.json` и в `frontend/AGENTS.md`.

Почему React + Vite, а не Next.js: приложение — одноэкранный внутренний инструмент без SSR, SEO и серверных маршрутов; Vite даёт быстрый dev-сервер с прокси и простой статический билд, который отдаёт Nginx.

Почему shadcn/ui, а не готовый UI-набор: правила `rules/frontend.md` требуют доступных примитивов, а не самописных элементов управления; shadcn/ui даёт готовые, читаемые исходники компонентов, которые остаются в репозитории и правятся под нужные состояния. Всё, что нужно приложению, — `button`, `input`, `label`, `card`, `badge`, `alert`, `separator`, `table` (и `tooltip` при необходимости).

Почему `lucide-react`: иконки всегда идут в паре с текстом, иконка никогда не единственный носитель смысла.

Альтернативы, отклонённые: `react-router-dom` (одна страница), Redux/Zustand (серверное состояние закрывает TanStack Query, транзиентное — локальный `useState`), `react-hook-form` (два поля и два submit-а, форма без сложной валидации), Axios (типизация из OpenAPI важнее), `zod` (runtime-валидация дублирует проверки backend), Recharts/табличные библиотеки (нет аналитики).

### 2. TypeScript 5.9.3, а не 7.x

Актуальный `latest` — TypeScript 7.0.2 (нативный переход на Go), и он заметно быстрее. Но на момент планирования он несовместим с экосистемой проекта. Ограничение задают **два** пакета, и оба требуют ветку 5.x:

- `openapi-typescript@7.13.0` объявляет `peerDependencies: { "typescript": "^5.x" }` — это генератор типов, от которого зависит весь слой API;
- `typescript-eslint@8.72.2` объявляет `peerDependencies: { "typescript": ">=4.8.4 <6.1.0" }` — линтер.

TypeScript 6.0.3 удовлетворяет второму ограничению, но не первому; TypeScript 7.0.2 не удовлетворяет ни одному. Поэтому фиксируется TypeScript 5.9.3 — последняя стабильная версия ветки 5.x, совместимая с обоими инструментами. Переход на TypeScript 7 выполняется отдельным изменением после появления поддержки в `openapi-typescript` и `typescript-eslint`.

Уточнение к предыдущей редакции этого документа: ограничение `typescript: ^5.x` относится к `openapi-typescript`, а не к `openapi-fetch`. У `openapi-fetch@0.17.0` peer- зависимостей нет вовсе (проверено по манифесту версии в реестре), а `typescript: ^5.9.3` указан у него только в `devDependencies` — это версия для разработки самого пакета и на потребителя не влияет.

### 4. Типы API и клиент: `openapi-typescript` + `openapi-fetch`

Типы генерируются одной командой из репозиторной спецификации:

```
npm run api:types   # openapi-typescript ../backend/openapi/swagger.yaml -o src/api/schema.d.ts
```

Клиент создаётся один раз в `src/api/client.ts`:

```ts
export const api = createClient<paths>({ baseUrl: "/" });
```

Пути в спецификации уже начинаются с `/api/v1/...`, поэтому `baseUrl` — `/` и префикс не дублируется. Все вызовы идут относительными путями, браузер обращается к тому же origin.

Почему `openapi-fetch`, а не ручной `fetch` с рукописными типами: путь, метод, параметры, тело запроса и коды ответов проверяются компилятором по спецификации; изменение контракта ломает сборку, а не runtime. Почему не `openapi-react-query`: он добавляет вторую абстракцию поверх TanStack Query; хуки пишутся вручную и остаются читаемыми.

Состояние сервера — `TanStack Query`: `queryKey: ["crm-clients", q]`, `["links"]`. После успешного `POST /api/v1/links` хук-мутация вызывает `invalidateQueries({ queryKey: ["links"] })`, поэтому список обновляется без ручного `refetch` из компонентов. Инвалидация выполняется в фоне и не ожидается: подтверждение сохранения показывается сразу, а список обновляется позже. Сбой обновления списка не отменяет уже сохранённую связь.

Поиск записи на сайте и создание связи оформлены как мутации, а не как фоновые загрузки: обе операции запускаются только по явному действию сотрудника. Поиск клиентов в основной базе — обычный `useQuery` с ключом по отправленной строке запроса, поэтому смена текста в поле сама по себе ничего не запрашивает.

Повторный поиск с тем же текстом выполняется через `refetch()` того же запроса: без этого после ошибки сотрудник не смог бы повторить поиск, не изменив введённое (query key не меняется, а новый запрос не создаётся). Пока запрос уже выполняется, повторное нажатие не отправляет второй параллельный запрос.

Реализация запроса вынесена в отдельную переменную `fetchImplementation` и передаётся в клиент явно: `openapi-fetch` заимствует глобальный `fetch` один раз — при создании клиента, — поэтому подменить его позже через глобальное окружение нельзя. Тесты подменяют запрос через `setFetchImplementation`, production-код обращается к `globalThis.fetch` без промежуточных слоёв.

### 5. Один экран и модель состояния

Рабочий экран состоит из четырёх пронумерованных шагов и раздела сохранённых связей. Состояние разбито на две части:

- серверное — TanStack Query (кандидаты, запись сайта, список связей);
- транзиентное UI — локальное состояние (`src/lib/workflow.ts`): текст поиска, выбранный `crm_id`, введённый номер, признак актуальности загруженной записи сайта.

Ключевое правило: пара актуальна только если совпадают обе её части. Запись сайта хранится вместе с номером `crm_id`, для которого она была загружена, и с номером, по которому ведётся поиск. Актуальность снимается при любом из событий:

| Событие | Что происходит с загруженной записью сайта | Сохранение |
| --- | --- | --- |
| изменён введённый номер записи | запись помечается «требует повторного поиска» | недоступно |
| изменён выбранный клиент основной базы (в том числе повторный выбор того же) | запись помечается «требует повторной проверки» | недоступно |
| возвращение к списку кандидатов по действию «Изменить выбор» | запись помечается «требует повторной проверки» | недоступно |

Защита дублируется в трёх местах: визуально — запись показывается как недействительная и не подставляется в блок сверки как действительная; в проверке актуальности — `isPairCurrent` дополнительно требует, чтобы номер возвращённой записи совпадал с номером поиска (`site.record.id === site.loadedForSiteId`), иначе запись сайта могла бы оказаться не той, которую сотрудник проверял; и в обработчике сохранения — перед отправкой запроса сверяется, что `crm_id` совпадает с тем, для которого загружена запись сайта, и что номер записи совпадает с введённым. Если проверка не проходит, запрос не отправляется, а интерфейс объясняет, что запись на сайте нужно найти заново.

Ответ с номером, отличным от запрошенного (или вовсе без номера), не показывается как найденная запись: поиск переводится в состояние ошибки с объяснением «Полученная запись не соответствует введённому номеру…», и сохранить такую пару нельзя. Нормализация номера — обрезка пробелов с обеих сторон: backend отдаёт `id` без окружающих пробелов (`adapters/outbound/csvutil/reader.go` обрезает поля при чтении), а сотрудник может ввести номер с пробелами.

Признак «идёт поиск записи» берётся из состояния сценария (`state.site.status === 'loading'`), а не из `isPending` мутации: мутация остаётся «в работе» до завершения сетевого вызова, даже если сотрудник уже сменил номер, и кнопка поиска выглядела бы зависшей. Идентификатор запроса при этом сохраняется: поздний ответ прежнего поиска не применяется.

### 5.1. Защита от запоздавшего ответа поиска

Асинхронный ответ может прийти уже после того, как сотрудник сменил клиента или номер записи. Такой ответ не должен восстанавливать актуальность пары.

Механизм — идентификатор запроса: счётчик, который растёт при каждом поиске. Идентификатор хранится в состоянии вместе с загруженной записью, поэтому reducer может отличить актуальный ответ от устаревшего. Смена клиента, открытие повторного выбора, изменение номера и начало нового поиска обнуляют идентификатор — после этого любой ответ с прежним идентификатором игнорируется и не меняет состояние интерфейса (ни успешный, ни ошибочный).

Почему не просто «сравнить клиента и номер в ответе»: ответ может прийти для той же пары, но уже устаревшей (смена A → C → A возвращает ту же пару, но она снова требует проверки). Идентификатор запроса отражает именно факт «этот ответ — от текущего поиска».

### 5.2. Повторное сохранение той же пары

После успешного сохранения в состоянии запоминается сама сохранённая пара (`crm_id` и `site_id`). Пока текущая пара совпадает с сохранённой, сохранение заблокировано — не только кнопкой, но и проверкой в обработчике, поэтому повторный запрос не уходит даже при вызове из другого места. Блокировка снимается, когда сотрудник меняет клиента или номер записи: тогда текущая пара перестаёт совпадать с сохранённой, и сохранить можно уже другую пару.

Пока идёт запрос на сохранение, менять клиента и номер записи нельзя: и элементы управления заблокированы, и обработчики отказываются менять данные — запрос уходит с той парой, которую сотрудник уже проверил. По той же причине во время сохранения недоступен поиск записи на сайте: кнопка «Найти запись на сайте» отключена, а обработчик поиска отказывается выполнять запрос, поэтому повторный GET за записью не уходит, а найденная ранее запись остаётся на экране.

Почему сбрасывается и при повторном выборе того же клиента: после возврата к списку сотрудник мог изменить свой выбор, и оставленная запись сайта уже не подтверждена для той пары, которую сотрудник собирается сохранить. Сброс стоит одного лишнего нажатия и убирает риск сохранить связь для другого человека.

Почему без единого глобального стейта: сценарий линейный и короткий; локальное состояние рядом с местом использования не требует синхронизации и не добавляет зависимостей.

Три замечания к таблице, важные для её честности:

- `invalid_query` и `query_empty` — разные ситуации: первый означает, что имя не передано, второй — что переданы только пробелы. Клиентская проверка пустого поля выполняется до запроса, поэтому второй код пользователю практически не показывается.
- `link_not_found` и `timeout` в текущей конфигурации сервиса практически недостижимы (`link_not_found` не производится ни одним адаптером, а у обработчиков нет собственного таймаута — сервер ограничивает запись 30 секундами на уровне HTTP-сервера). Коды оставлены в таблице как защита: если backend их начнёт возвращать, интерфейс покажет осмысленный текст, а не «неизвестная ошибка».
- `crm_already_linked` и `site_already_linked` нельзя сводить к одному сообщению: ограничения уникальности на `crm_id` и `site_id` независимы, поэтому занятый идентификатор может принадлежать другой паре. Backend не сообщает, какая именно пара занята, поэтому интерфейс не имеет права утверждать, что текущая пара уже сохранена, и направляет сотрудника к списку сохранённых связей.

Тексты backend не показываются как есть: например, `last_name_mismatch` превращается в «Фамилии в основной базе и на сайте не совпадают…». Коды ответов, трассировки стека и внутренние детали на экран не выводятся. Неизвестный код и сетевой сбой получают отдельные запасные сообщения («Не удалось получить данные. Проверьте подключение и попробуйте ещё раз.»). Ни один текст для сотрудника не содержит слов «сервер», «сервис», «API», «JSON» и прочих технических терминов. При ошибке введённые значения, выбранный кандидат и уже загруженная запись остаются на экране.

Почему маппинг по `code`, а не по HTTP-статусу: `code` объявлен в backend как стабильный и предназначенный для фронтенда (`handlers/response.go:18`), а статус `499` нестандартный и часть статусов совпадает у разных ситуаций.

### 8. Визуальное направление

Спокойный светлый рабочий интерфейс без декоративного dashboard:

- фон страницы — нейтральный светло-серый, рабочие поверхности (блоки шагов, карточки записей, таблица) — белые; одна рамка 1 px вместо тяжёлых теней;
- один акцентный цвет — спокойный синий; семантические цвета — зелёный (успех), янтарный (предупреждение), красный (ошибка); цвет всегда дополнен текстом или знаком, чтобы состояние не определялось только цветом;
- типографика: системный шрифт, основной текст 16 px, вспомогательный 14–15 px, заголовок страницы 24–28 px, имя кандидата — самый крупный текст в карточке;
- крупные элементы управления: поля и кнопки не ниже 44 px по высоте, между кнопками достаточно расстояния, чтобы исключить случайное нажатие;
- чёткая иерархия: один визуально главный блок — «Проверьте данные» с кнопкой «Сохранить связь»; остальные шаги выглядят спокойнее;
- умеренные радиусы (8–12 px), единая шкала отступов, никаких градиентов, стекла, теней-«подсветок» и анимаций, кроме уважающих `prefers-reduced-motion` переходов;
- таблица сохранённых связей — простая, без сортировки, фильтров и декоративной метрики; на узких экранах она прокручивается по горизонтали в области с доступным именем и видимым фокусом (вариант с карточками отклонён: он ломает нативную семантику таблицы и требует дублировать разметку данных).

Почему не «красиво и modern»: целевая аудитория — люди, которые могут бояться ошибиться; задача интерфейса — снизить тревожность и исключить ошибку, а не произвести впечатление.

### 9. Доступность

- целевой уровень — WCAG 2.2 AA: контраст текста не ниже 4.5:1, границ и значков — не ниже 3:1;
- у каждого поля постоянная видимая подпись, связанная через `label for`; подсказка и текст ошибки связаны через `aria-describedby`; ошибочное поле получает `aria-invalid`;
- весь сценарий выполняется с клавиатуры: `Enter` в поле поиска отправляет поиск, `Enter` в поле номера — поиск записи, активация — `Enter`/`Space`;
- порядок перехода по `Tab` совпадает с порядком шагов: поле поиска → кнопка поиска → выбор кандидата → изменение выбора → поле номера записи → кнопка поиска записи → кнопка сохранения → выгрузка CSV; порядок закреплён тестом с настоящими переходами `Tab`, без программной установки фокуса;
- видимый фокус — `focus-visible` с кольцом 2 px и отступом, `outline` не удаляется нигде;
- интерактивные элементы — не меньше 44×44 CSS px, где это достижимо; указатель мыши не является единственным способом;
- загрузка, число результатов, ошибки и подтверждение объявляются через `role="status"` / `aria-live="polite"`, ошибки — `role="alert"`; результат поиска записи сайта объявляется отдельной живой областью, причём одно состояние не объявляется двумя областями; фокус сам по себе не перемещается, чтобы не терять место пользователя;
- фокус перемещается только по действиям сотрудника: после выбора клиента — на имя выбранного клиента, после «Изменить выбор» — на список найденных клиентов (или на поле поиска, если выбирать пока нечего); обновление результатов само по себе фокус не двигает;
- таблица — настоящая `<table>` с `<caption>` и `<th scope>`; на узких экранах она прокручивается по горизонтали, а область прокрутки имеет `role="region"`, доступное имя, `tabIndex="0"` и видимый фокус;
- текст в полях ввода не уменьшается на широких экранах: базовый размер примитива — 16 CSS px (в примитиве нет `md:text-sm`);
- при масштабе 200 % и на ширине 320 px поля, кнопки и обе записи остаются читаемыми и не обрезаются (эта проверка требует браузерного прогона и в автоматических проверках не подтверждена);
- системная настройка уменьшения анимации учитывается: глобальное правило `@media (prefers-reduced-motion: reduce)` сокращает длительность анимаций и переходов, включая стили примитивов интерфейса; при настройке по умолчанию тема и поведение не меняются.

### 10. Локальная разработка: Vite proxy, без CORS

В `vite.config.ts`:

```ts
server: {
  proxy: {
    "/api": { target: "http://localhost:8080", changeOrigin: true },
  },
},
```

Приложение всегда обращается к `/api/v1/...` относительно текущего origin, поэтому браузер не делает кросс-доменный запрос и CORS в backend не нужен.

### 11. Production: многоступенчатый Docker и Nginx с прокси

`frontend/Dockerfile`:

- стадия сборки: `node:24-alpine`, `npm ci`, `npm run build` → `dist/`;
- стадия запуска: `nginx:1.29-alpine`, копируются только `dist/` и `nginx.conf`; исходники, `node_modules` и dev-зависимости в итоговый образ не попадают.

`frontend/nginx.conf`:

```nginx
server {
  listen 80;
  server_name _;
  root /usr/share/nginx/html;
  index index.html;

  location /api/ {
    proxy_pass http://backend:8080;
    proxy_set_header Host $host;
  }

  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

Решения:

- `proxy_pass` без URI-части сохраняет путь запроса как есть: `/api/v1/links` уходит на `http://backend:8080/api/v1/links`;
- заголовки `X-Forwarded-For` и `X-Real-IP` намеренно не проксируются: backend вызывает `SetTrustedProxies(nil)` (`router.go:19`) и не доверяет таким заголовкам, а передавать их всё равно бессмысленно;
- `try_files … /index.html` даёт SPA-fallback: любой неизвестный путь открывает приложение, а не 404;
- `location /api/` проксирует только API; Swagger UI backend (`/docs/`) и спецификация (`/openapi.json`, `/openapi.yaml`) остаются на порту backend и через фронтенд не открываются.

### 12. Compose

В существующий `docker-compose.yml` добавляется один сервис:

```yaml
  frontend:
    build: ./frontend
    depends_on:
      backend:
        condition: service_healthy
    ports:
      - "127.0.0.1:${FRONTEND_PORT:-3000}:80"
```

Опубликованные порты `backend` и `frontend` привязаны к `127.0.0.1`, поэтому стек не доступен из сети, где нет контроля доступа (PostgreSQL был привязан так же). Внутренние порты контейнеров, healthcheck, зависимости сервисов, том `pgdata` и миграции не меняются. `docker compose down -v` по-прежнему не используется.

Это ограничение публикации, а не механизм доступа: сервисы по-прежнему не имеют аутентификации, поэтому приложение с реальными персональными данными нельзя выставлять наружу (решение 19).

### 13. Тестирование

Vitest (окружение `jsdom`, `globals: true`) + React Testing Library + `user-event`; HTTP замокан на уровне `fetch`, реальные CSV не читаются.

Покрытие: поиск (результат, пустой результат, ошибка, защита от повторного запроса), выбор кандидата (отображение ФИО, даты, организации, номера, «Изменить выбор»), поиск записи сайта (найдена, не найдена, сброс устаревшей записи после правки номера), блок сверки (видны обе записи и оба номера, сохранение заблокировано без записи сайта), сохранение (успех, блокировка повторного нажатия, ошибки `409` и `422` с понятным текстом и сохранёнными полями), список связей (обновление после сохранения, пустое состояние, наличие ссылки на CSV), доступность (автоматическая проверка `axe-core` по отрендеренному контейнеру).

Дополнительно покрываются сценарии защиты от гонок и повторных действий:

- запоздавший успешный ответ поиска записи после смены клиента A → C → A не восстанавливает актуальность пары;
- запоздавший ответ после изменения номера записи не применяется;
- результат последнего запроса применяется, а устаревшая ошибка не заменяет состояние нового поиска;
- номер возвращённой записи должен совпадать с номером поиска, иначе сохранение запрещено;
- повторное сохранение уже сохранённой пары не отправляет второй запрос, а подтверждение называет именно сохранённую пару;
- пока идёт сохранение, клиента и номер записи изменить нельзя; после неудачного запроса данные можно исправить и повторить;
- во время сохранения поиск записи на сайте недоступен и повторный GET за записью не уходит, а найденная запись остаётся на экране;
- изменённый текст поиска не предлагает прежние результаты, а ошибка поиска не выглядит как пустой успешный поиск;
- пустой номер записи на сайте даёт понятное сообщение, помечает поле ошибочным и не приводит к запросу;
- до успешной загрузки списка связей ссылки на выгрузку CSV нет — доступна отключённая кнопка;
- повторный поиск после ошибки выполняется с тем же текстом и приводит к результату; параллельный дубль запроса не отправляется;
- изменение номера записи во время поиска делает прежний поиск недействительным, поиск нового номера доступен, поздний ответ прежнего поиска не применяется;
- ответ записи сайта без номера или с чужим номером не показывается как найденная запись и не позволяет сохранить связь;
- подтверждение сохранения появляется до завершения обновления списка связей, список обновляется после;
- ответ без JSON (страница шлюза) не показывается сотруднику: вместо него выводится сообщение о временной недоступности данных;
- фокус после выбора клиента и после «Изменить выбор» проверяется через `document.activeElement`;
- область прокрутки таблицы имеет доступное имя и доступна с клавиатуры.

Каждая из этих проверок дублируется юнит-тестом состояния: без защиты в reducer соответствующие тесты падают, поэтому они действительно ловят дефект, а не фиксируют текущее поведение.

`axe-core` покрывает лишь часть требований WCAG 2.2 AA, поэтому автоматическая проверка дополняется эвристическим проходом по сценарию и ручной проверкой контраста, фокуса и размеров элементов.

Границы автоматических проверок: `axe-core` в jsdom не измеряет контраст (нет canvas), а чтение `computed style` в браузере не выполняется. Поэтому утверждения о контрасте, поведении при ширине 320 px и масштабе 200 %, работе со screen reader и удобстве для сотрудников фонда в отчётах не выдаются: выполняются только DOM-проверки, статический просмотр кода и расчёт контраста вручную.

### 15. Календарные даты: разбор компонентов без временной конвертации
`birthday` — календарная дата в формате `YYYY-MM-DD` (`handlers/dto.go:30`), а не метка времени. Frontend SHALL разбирать её на компоненты и собирать «ДД.ММ.ГГГГ» без обращения к `Date` и без учёта часового пояса.

Реализация: строка делится по `-` на год, месяц и день, части дополняются нулями до двух цифр и соединяются точками. Значение, которого нет или которое не разбирается, заменяется обозначением отсутствия данных.

Почему не `new Date("1982-04-15")`: по стандарту ISO такая строка разбирается как полночь по UTC, а форматирование в локальный часовой пояс в зонах со смещением назад сдвигает дату на сутки назад — сотрудник увидит «14.04.1982» у клиента с датой рождения 15 апреля.

`created_at` (`handlers/dto.go:45`) — дата и время в формате RFC 3339 с указанием смещения, поэтому она разбирается обычным `new Date(value)` и показывается в локальном часовом поясе браузера в формате «ДД.ММ.ГГГГ, ЧЧ:ММ». Разные часовые пояса у сотрудников могут дать разное локальное время одной и той же связи — для внутреннего инструмента это приемлемо, а замена на UTC сделала бы время нечитаемым.

Проверка: тест с датой «1982-04-15» выполняется в часовом поясе, отличном от UTC (в тестовом окружении задаётся `TZ`), и результат обязан остаться «15.04.1982».

### 16. Необязательные поля в сгенерированных типах
В спецификации `backend/openapi/swagger.yaml` схемы ответов не содержат списка `required` (он есть только у `handlers.CreateRequest`), поэтому `openapi-typescript` генерирует все поля ответов как необязательные: `id`, `full_name`, `birthday`, `clinic`, `short_name`, `last_name`, `created_at` могут отсутствовать в типах. Менять backend-спецификацию в рамках этого change нельзя.

Решение: работать с необязательными полями безопасно и без обхода проверки типов:

- вспомогательные функции в `src/lib/format.ts` принимают `string | undefined` и возвращают текст для показа: значение, если оно есть, и обозначение отсутствия данных («—») иначе;
- запись без `id` не может быть выбрана для сохранения: номер показывается как «—», выбор недоступен с пояснением, а запрос с пустым номером не отправляется;
- идентификаторы для сохранения берутся только из реально пришедших значений, без подстановки заглушек.

Почему без `!`, `as any` и дублирования DTO вручную: такие приёмы отключают проверку типов именно там, где ответ сервиса может оказаться неполным, и размножают контракт, который уже описан в спецификации. Почему без runtime-валидации всего API (например, `zod`): контракт фиксирован backend, дублировать его проверкой целиком — лишняя абстракция; достаточно аккуратно обработать отсутствие отдельных полей.

### 17. Проверка типов охватывает все части проекта
Проект создаётся каркасом Vite с несколькими конфигурациями TypeScript (`tsconfig.json` с `references` на `tsconfig.app.json` и `tsconfig.node.json`). Команда проверки типов SHALL запускаться через `tsc -b` (`npm run typecheck` → `tsc -b`), чтобы проверялись все проекты сразу — исходный код приложения, конфигурация сборки и файлы тестов, — а не только один из них.

Почему `tsc -b`, а не `tsc --noEmit`: при `references` команда `--noEmit` на верхнеуровневом файле без включённых ссылок проверяет только его самого; `tsc -b` обходит граф проектов. Если тесты попадут в отдельный конфиг, он добавляется в `references` — иначе проверка типов будет выглядеть успешной, пропуская часть кода.

### 18. CLI shadcn закреплён конкретной версией
Инициализация и добавление примитивов выполняются версией `shadcn@4.23.0` (`npx shadcn@4.23.0 init`, `npx shadcn@4.23.0 add …`), а не плавающим `latest`: результат `init` (конфигурация `components.json`, тема, набор зависимостей) должен быть воспроизводим и не должен меняться при появлении новой версии CLI.

Повторная интерактивная настройка во время реализации не требуется: `components.json` и примитивы `src/components/ui/*` попадают в репозиторий, а CLI вызывается только для добавления нового примитива. Если конкретная версия CLI потребует интерактивных ответов, они фиксируются один раз и результат сохраняется в репозитории; повторный запуск инициализации не планируется.

### 19. Ограничение по развёртыванию: контроль доступа не входит в объём
Авторизация, вход и роли намеренно не входят в scope этого change: backend их не имеет, и их добавление означало бы изменение HTTP-контракта и модели безопасности backend, что запрещено границами задачи.

Но приложение показывает персональные данные клиентов, поэтому в документации фиксируется явное ограничение: текущая версия предназначена для доверенного локального или изолированного окружения и не должна выставляться в публичное или незащищённое сетевое развёртывание с реальными данными без отдельного решения по контролю доступа. Ограничение фиксируется в `README.md`, в `frontend/AGENTS.md` и в `proposal.md`; никаких механизмов контроля доступа при этом не добавляется.

## Risks / Trade-offs

- **TypeScript 5.9.3 вместо актуального 7.0.2** → Выбран сознательно: ограничение задают `openapi-typescript@7.13.0` (`peer: typescript ^5.x`) и `typescript-eslint@8.72.2` (`peer: typescript >=4.8.4 <6.1.0`). TypeScript 6.0.3 не проходит первое ограничение, TypeScript 7.0.2 — ни одно. Переход на 7.x выполняется отдельным изменением после обновления этих пакетов; до него `npm ci` не даст конфликта peer-зависимостей.
- **Минимальный Node.js поднят до `^22.22.2 || ^24.15.0 || >=26.0.0`** → Ограничение задаёт `jsdom@31` (тестовое окружение), а не Vite: сам Vite 8 допускает Node 20.19+. Разработчикам с Node 20 или 22.12–22.22 придётся обновить Node — это осознанная плата за свежий стек; в образе сборки используется `node:24-alpine` (актуальная ветка 24 — 24.22.3), он в диапазон попадает.
- **Vite 8 и `@vitejs/plugin-react` 6.3.0** → Обе версии свежие; связка подтверждена peer-зависимостью `vite ^8.0.0`, дополнительные peer- зависимости плагина помечены optional и установки не требуют.
- **Ошибку выгрузки CSV интерфейс не перехватывает** → Выгрузка идёт обычной ссылкой (требование `rules/frontend.md`), а при ошибке backend отдаёт JSON, который браузер покажет сам. Вместо «своей» ошибки выгрузки интерфейс блокирует выгрузку, пока не загружен список связей, и это же условие проверяется в тестах.
- **Фиксированная версия CLI `shadcn@4.23.0`** → Конфигурация `components.json` и примитивы сохраняются в репозитории, поэтому результат не зависит от того, какая версия CLI выйдет позже.
- **Проверка типов через `tsc -b`** → Проверяются все проекты TypeScript (приложение, конфигурация сборки, тесты); альтернатива с `tsc --noEmit` могла бы молча пропускать часть кода.
- **Ответы без части полей возможны** → В спецификации нет списков `required`, поэтому поля сгенерированных типов необязательные. Интерфейс показывает обозначение отсутствия данных и не даёт сохранить связь без идентификаторов; контракт при этом не дублируется и не валидируется целиком на runtime.
- **Отдельный порт фронтенда (по умолчанию 3000)** → Для локальной демонстрации нужен второй адрес; альтернатива — отдавать фронтенд на порту backend, но тогда пришлось бы встроить статику в Go-сервис, что ломает разделение слоёв.
- **Прокси Nginx добавляет сетевой хоп** → Внутри Compose это локальная сеть Docker; влияние на задержку пренебрежимо мало, зато исчезает потребность в CORS и появляется единый origin.
- **Таблица связей без сортировки и фильтров** → Для текущего объёма данных (сотни–тысячи строк) это сознательное упрощение: сложные таблицы противоречат требованию «никакого декоративного dashboard» и повышают риск ошибки. Возвращать поиск по таблице следует отдельным изменением с обновлением спецификации.
- **Дата сохранения показывается в локальном времени браузера** → Backend отдаёт RFC 3339 в UTC. Для сотрудников фонда в одном часовом поясе локальное время привычнее; при расхождении часовых поясов между сотрудниками метка времени в списке может отличаться от времени сервера — это приемлемо для внутреннего инструмента. Дата рождения при этом не пересчитывается (решение 15).
- **Проверка доступности частично автоматизирована** → `axe-core` не покрывает WCAG 2.2 AA полностью; остаток закрывается эвристическим проходом и ручной проверкой. Утверждения о соответствии WCAG в отчётах не выдаются без фактической проверки.
- **Ответ без JSON не разбирается как ошибка backend** → прокси может ответить страницей шлюза, когда backend недоступен. `openapi-fetch` отдаёт такое тело строкой, поэтому клиент определяет формат ответа по `Content-Type` и показывает сотруднику сообщение о временной недоступности данных, не выводя текст ответа.
- **Браузерные проверки не выполнялись в этой итерации** → измерение контраста в браузере, прогон на ширине 320 px и при масштабе 200 %, работа со screen reader и тестирование с сотрудниками фонда не подтверждены; они указаны как ограничения, а не как выполненные проверки.
- **Изменение `docker-compose.yml` и `README.md` затрагивает существующие файлы** → Правки минимальны и аддитивны: один сервис в Compose, один раздел в README; сервисы `db`, `migrate`, `backend` и том `pgdata` не меняются.
- **Приложение не имеет контроля доступа** → Ограничение по развёртыванию зафиксировано явно (решение 19, `README.md`, `frontend/AGENTS.md`): версия предназначена для доверенного локального или изолированного окружения. Публичное развёртывание с реальными персональными данными требует отдельного решения по контролю доступа, которое в этот change не входит.

## Migration Plan

1. Создать папку `frontend/` с каркасом Vite, настроить strict TypeScript, Tailwind CSS v4 и shadcn/ui, добавить скрипты проверки.
2. Сгенерировать типы API из `backend/openapi/swagger.yaml`, собрать слой `src/api` (клиент, хуки, маппинг ошибок).
3. Реализовать четыре шага сценария и раздел сохранённых связей: состояние актуальности пары в `src/lib/workflow.ts`, безопасный разбор и показ дат в `src/lib/format.ts`, затем тесты.
4. Добавить `frontend/Dockerfile`, `frontend/nginx.conf`, сервис `frontend` в `docker-compose.yml`.
5. Обновить `README.md` (включая предупреждение о развёртывании без контроля доступа), `openspec/config.yaml`, корневой `AGENTS.md`, добавить `frontend/AGENTS.md` с требованием версии Node.js и тем же предупреждением.
6. Проверить локально и в Docker: `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`, `docker compose config`, сборка и запуск стека, проверка `GET /` и `GET /api/v1/links` через порт фронтенда.

Данные и обратная совместимость API не затрагиваются: backend не меняется, миграции не выполняются. Откат — удаление папки `frontend/` и сервиса `frontend` из Compose; backend продолжает работать как раньше.
