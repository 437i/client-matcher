# Proposal

## Why

Сегодня единственный способ связать ID клиента в CRM с ID клиента на сайте — ручной вызов API: для сотрудника фонда это означает терминал, JSON, `crm_id`/`site_id` в теле запроса и самостоятельное чтение кодов ошибок (`409`, `422`, `404`). Рабочий инструмент, которым пользуются люди с разной, часто низкой компьютерной грамотностью, в таком виде недоступен: связь не создаётся, её нельзя проверить глазами перед сохранением, а список сохранённых пар и CSV-выгрузка недоступны без отдельного инструмента.

Backend уже предоставляет весь нужный контракт: поиск по CRM, загрузка записи сайта по известному ID, создание связи с проверкой фамилии и даты рождения, список связей и выгрузка CSV, а также машинно-читаемая спецификация OpenAPI 3.1. Нужен слой представления, который превратит этот контракт в один понятный русскоязычный экран: найти человека, выбрать правильную запись, найти его запись на сайте, увидеть обе записи рядом, сохранить связь и выгрузить результат.

## What Changes

- Появляется папка `frontend/` — одностраничное приложение (SPA) на React 19 + strict TypeScript + Vite, отдельное от Go-модуля `backend/` и без собственной бизнес-логики.
- Рабочий сценарий реализован на одном экране: поиск человека в основной базе (CRM) → выбор кандидата → ввод номера записи на сайте → загрузка и показ записи сайта → блок сверки обеих записей и обоих ID → явное сохранение связи → постоянное подтверждение успеха и обновлённый список сохранённых связей → выгрузка CSV.
- Связь актуальна только когда совпадают обе её части: изменение введённого номера записи, изменение выбранного клиента основной базы и возврат к списку кандидатов сбрасывают загруженную запись сайта, помечают её как требующую повторной проверки и делают сохранение недоступным — проверка дублируется в обработчике сохранения.
- Конфликт «идентификатор уже занят» различается для клиента основной базы и для записи сайта: интерфейс не утверждает, что текущая пара уже сохранена, и направляет сотрудника к списку сохранённых связей, потому что backend не сообщает, какая именно пара занята идентификатор.
- Типы API генерируются из репозиторной спецификации `backend/openapi/swagger.yaml` командой `openapi-typescript`; HTTP-вызовы выполняются типизированным клиентом `openapi-fetch`. Параллельных DTO во фронтенде не заводится.
- Серверное состояние (список найденных кандидатов, запись сайта, список связей) управляется `TanStack Query`; ошибки API с телом `{ code, message }` переводятся в понятные русские сообщения с одним безопасным следующим шагом.
- Оформление: Tailwind CSS v4 + примитивы shadcn/ui, иконки `lucide-react`. Интерфейс — спокойный светлый рабочий экран без декоративного dashboard, с постоянными подписями полей, крупными элементами управления (ориентир 44×44 CSS px), видимым фокусом и целевой доступностью WCAG 2.2 AA.
- Локальная разработка: Vite dev-сервер проксирует `/api` на `http://localhost:8080`, поэтому в браузере используются только относительные пути и CORS не нужен.
- Сборка и запуск: многоступенчатый `frontend/Dockerfile` (сборка Vite → раздача `dist/` через Nginx), конфигурация Nginx с fallback на SPA и проксированием `/api/` на `backend:8080` по сети Compose. В существующий `docker-compose.yml` добавляется сервис `frontend` на отдельном настраиваемом порту (по умолчанию `3000`); порт и поведение backend API (8080) сохраняются, CORS в backend не добавляется.
- Тесты интерфейса: Vitest + React Testing Library + `user-event`, HTTP замокан, реальные CSV не читаются.
- Документация: в корневом `README.md` добавляется раздел о фронтенде; в `openspec/config.yaml` добавляется краткий контекст о фронтенде; корневой `AGENTS.md` дополняется минимально и согласованно с уже имеющимися разделами о frontend.

Вне рамок изменения: изменение бизнес-логики, HTTP-маршрутов, JSON-полей, кодов статусов и mapping ошибок backend; миграции БД; CSV-адаптеры и форматы источников; аутентификация и авторизация; клиентский роутинг и SPA-навигация; глобальные стейт-менеджеры; серверный рендеринг; мобильное приложение; реальное тестирование с сотрудниками фонда.

Ограничение по развёртыванию: контроль доступа в объём не входит, поэтому версия предназначена для доверенного локального или изолированного окружения. Публичное или незащищённое сетевое развёртывание с реальными персональными данными клиентов не поддерживается без отдельного решения по контролю доступа; предупреждение фиксируется в документации проекта.

## Capabilities

### New Capabilities

- `frontend-app`: одноэкранный русскоязычный интерфейс ручного сопоставления клиентов — поиск и выбор кандидата в основной базе, поиск записи на сайте по номеру, сверка обеих записей, явное сохранение связи, список сохранённых связей, выгрузка CSV, состояния интерфейса и требования доступности для пользователей с низкой компьютерной грамотностью.
- `frontend-delivery`: воспроизводимая сборка и запуск фронтенда — локальный dev-сервер с прокси, типы API из репозиторной спецификации, многоступенчатый Docker-образ с Nginx, сервис в существующем Compose и проверки без изменения backend.

### Modified Capabilities

- Нет: требования `api-documentation` не меняются — спецификация остаётся источником истины для клиентских типов, а её описание не редактируется.

## Impact

- Код: новая папка `frontend/` (Vite-проект, `src/api` со сгенерированными типами и клиентом, `src/features` с поиском/выбором/поиском на сайте/сверкой/сохранением/списком связей, компоненты UI, тесты). Backend не изменяется.
- Контракт: используются существующие маршруты `GET /api/v1/crm-clients`, `GET /api/v1/site-clients/{id}`, `POST /api/v1/links`, `GET /api/v1/links`, `GET /api/v1/links/export.csv` без изменений; CORS-заголовки в backend не добавляются — браузер обращается к тому же origin.
- Артефакты: `frontend/Dockerfile`, `frontend/nginx.conf`, сервис `frontend` в `docker-compose.yml`, изменения `README.md`, `openspec/config.yaml`, корневого `AGENTS.md`.
- Зависимости: npm-пакеты `react`, `react-dom`, `@tanstack/react-query`, `openapi-fetch`, `lucide-react`, `tailwindcss`, `class-variance-authority`, `clsx`, `tailwind-merge`; dev-зависимости `vite`, `@vitejs/plugin-react`, `@tailwindcss/vite`, `typescript`, `openapi-typescript`, `vitest`, `jsdom`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `axe-core`, `eslint`, `typescript-eslint`. CLI `shadcn` используется на версии `4.23.0` и в зависимости приложения не остаётся. Минимальная версия Node.js — `^22.22.2 || ^24.15.0 || >=26.0.0` (ограничение задаёт `jsdom@31`), она же фиксируется в поле `engines` файла `package.json` и в образе сборки. Go-зависимости не меняются.
- Docker: добавляется один сервис в Compose; backend, БД, миграции и том `pgdata` не меняются; команда `docker compose down -v` по-прежнему не используется.
- Данные: интерфейс работает с теми же источниками, что и backend; содержимое `data/*.csv`, `testdata/*.csv` и `.env` во фронтенд не переносится и не читается тестами.
