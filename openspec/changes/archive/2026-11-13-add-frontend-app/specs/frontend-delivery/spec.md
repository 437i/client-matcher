# Spec Delta

## Purpose

Обеспечить воспроизводимую сборку и запуск фронтенда client-matcher: типы клиента выводятся из репозиторной спецификации OpenAPI, локальная разработка и production-контейнер обращаются к backend через прокси того же origin, а сервис фронтенда добавляется в существующий Compose без изменения backend.

## ADDED Requirements

### Requirement: Типы API выводятся из репозиторной спецификации
Клиентские типы SHALL генерироваться из файла `backend/openapi/swagger.yaml` одной документированной командой, SHALL быть единственным источником типов запросов и ответов, и ручное дублирование DTO во фронтенде SHALL NOT допускаться.

#### Scenario: Генерация типов
- **WHEN** выполняется команда генерации типов в папке `frontend/`
- **THEN** создаётся файл типов, соответствующий текущему содержимому `backend/openapi/swagger.yaml`

#### Scenario: Типы воспроизводимы
- **WHEN** команда генерации выполняется дважды подряд без изменения спецификации
- **THEN** второе выполнение не меняет сгенерированный файл

#### Scenario: Контракт не дублируется вручную
- **WHEN** проверяется код фронтенда
- **THEN** структуры запросов и ответов описаны только сгенерированными типами, а не объявлены вручную

#### Scenario: Спецификация не меняется
- **WHEN** сверяется состояние `backend/openapi/swagger.yaml`
- **THEN** файл не изменён этим изменением: контракт backend остаётся прежним

### Requirement: Локальная разработка обращается к backend через прокси
Dev-сервер SHALL проксировать путь `/api` на backend, запущенный локально, а приложение в режиме разработки SHALL использовать только относительные пути `/api/v1`, без отдельного API-origin и без требования к настройке CORS в backend.

#### Scenario: Запрос из dev-сервера
- **WHEN** выполняется запрос `GET /api/v1/crm-clients` через запущенный dev-сервер
- **THEN** запрос доходит до backend и возвращает его ответ без ошибки CORS в браузере

#### Scenario: Конфигурация прокси задана в проекте
- **WHEN** проверяется конфигурация dev-сервера
- **THEN** в ней указан прокси `/api` на `http://localhost:8080`

### Requirement: Production-контейнер отдаёт собранное приложение и проксирует API
Production-образ SHALL собираться в несколько ступеней, отдавать статические файлы собранного приложения через веб-сервер, перенаправлять неизвестные пути на индексный файл приложения и проксировать `/api/` на backend по сети Compose.

#### Scenario: Сборка образа
- **WHEN** собирается production-образ фронтенда
- **THEN** образ содержит только статические файлы собранного приложения и конфигурацию веб-сервера, а dev-зависимости и исходники в итоговый образ не попадают

#### Scenario: Приложение открывается по корню
- **WHEN** выполняется запрос корневого пути к контейнеру фронтенда
- **THEN** возвращается индексный файл собранного приложения

#### Scenario: Неизвестный путь открывает приложение
- **WHEN** выполняется запрос пути, которого нет на диске
- **THEN** возвращается индексный файл приложения со статусом 200, а не ошибка 404

#### Scenario: API-запрос проксируется
- **WHEN** выполняется запрос `GET /api/v1/links` к контейнеру фронтенда
- **THEN** ответ приходит от backend и содержит список связей

#### Scenario: Файлы окружения не попадают в образ
- **WHEN** проверяется содержимое контекста сборки фронтенда
- **THEN** файлы `.env` и `.env.*` исключены правилами `frontend/.dockerignore` и не попадают в образ

### Requirement: Compose запускает фронтенд отдельным сервисом без изменения backend
Существующий файл `docker-compose.yml` SHALL получить сервис фронтенда на отдельном настраиваемом порту по умолчанию 3000, при этом порт и поведение backend API SHALL сохраниться, а CORS-заголовки в backend SHALL NOT добавляться.

#### Scenario: Стек запускается целиком
- **WHEN** выполняется `docker compose up --build -d`
- **THEN** поднимаются база, миграции, backend и фронтенд, и приложение доступно на порту фронтенда

#### Scenario: Backend не изменён
- **WHEN** сравнивается сервис backend с прежней версией
- **THEN** его маршруты, порт, переменные окружения и том с тестовыми данными не изменились

#### Scenario: Порт настраивается
- **WHEN** задан параметр окружения с другим портом фронтенда
- **THEN** фронтенд публикуется на этом порту, а порт backend остаётся прежним

#### Scenario: Опубликованные порты доступны только с локального хоста
- **WHEN** разворачивается стек compose
- **THEN** опубликованные host-порты frontend и backend по умолчанию привязаны к `127.0.0.1`, поскольку приложение не реализует авторизацию и не должно быть доступно из сети, где нет контроля доступа

#### Scenario: CORS не требуется
- **WHEN** приложение обращается к API через прокси того же origin
- **THEN** в backend не появляется middleware, разрешающий кросс-доменные запросы

### Requirement: Проверки фронтенда доступны и воспроизводимы
Проект фронтенда SHALL предоставлять документированные команды для проверки типов, стиля, тестов, сборки и генерации типов API, и каждая команда SHALL завершаться успешно на чистом окружении.

#### Scenario: Набор команд
- **WHEN** проверяется список npm-скриптов
- **THEN** присутствуют отдельные команды проверки типов, линтинга, тестов, сборки и генерации типов API

#### Scenario: Типы проверяются
- **WHEN** выполняется команда проверки типов
- **THEN** она завершается успешно и охватывает весь исходный код приложения, включая тесты

#### Scenario: Проверка типов охватывает все части проекта
- **WHEN** выполняется команда проверки типов
- **THEN** она проверяет исходный код приложения, конфигурацию сборки и файлы тестов, а не только один из этих файлов

#### Scenario: Сборка воспроизводима
- **WHEN** выполняется команда сборки
- **THEN** она завершается успешно и создаёт каталог со статическими файлами приложения

#### Scenario: Вид проверок указан честно
- **WHEN** читается отчёт о выполненных проверках фронтенда
- **THEN** в нём явно разделены автоматические проверки, статический просмотр кода, расчёт контраста, реальный браузерный прогон, ручная проверка адаптивности и тестирование с сотрудниками; непроведённые проверки указаны как ограничения и не выдаются за выполненные

### Requirement: Минимальная версия Node.js зафиксирована и соблюдается
Проект фронтенда SHALL объявлять минимальную поддерживаемую версию Node.js в поле `engines` файла `package.json` и SHALL использовать в Docker-образе версию Node.js, удовлетворяющую этому минимуму и требованиям всех используемых инструментов.

#### Scenario: Минимум объявлен
- **WHEN** проверяется файл `package.json`
- **THEN** в поле `engines` указан минимальный диапазон версий Node.js, совместимый с требованиями всех зависимостей проекта

#### Scenario: Образ сборки подходит
- **WHEN** выбирается базовый образ Node.js для стадии сборки
- **THEN** его версия входит в объявленный диапазон и удовлетворяет минимальным требованиям инструментов проверки и сборки

### Requirement: Приложение разворачивается только в доверенном окружении
Приложение SHALL быть предназначено для доверенного локального или изолированного окружения, и документация SHALL явно предупреждать, что публичное или незащищённое сетевое развёртывание с реальными персональными данными не поддерживается, пока не принято отдельное решение по контролю доступа.

#### Scenario: Ограничение указано в документации
- **WHEN** читатель открывает документацию по запуску фронтенда
- **THEN** в ней есть явное предупреждение о том, что приложение нельзя выставлять в общий доступ без отдельного решения по контролю доступа

#### Scenario: Авторизация не выдумывается
- **WHEN** проверяется результат изменения
- **THEN** ни во frontend, ни в backend не добавлено механизмов входа, ролей или проверки прав доступа

#### Scenario: Ограничение публикации зафиксировано
- **WHEN** читатель открывает документацию по развёртыванию
- **THEN** в ней указано, что опубликованные порты по умолчанию доступны только с локального хоста и что этого недостаточно для публичного развёртывания с реальными данными

### Requirement: Тесты интерфейса не используют реальные данные клиентов
Тесты фронтенда SHALL использовать подставные HTTP-ответы и SHALL NOT читать, копировать или отправлять содержимое клиентских CSV-файлов, файлов окружения и других источников с персональными данными.

#### Scenario: Тесты изолированы
- **WHEN** выполняются тесты интерфейса
- **THEN** HTTP-запросы обслуживаются заглушками, а реальные файлы данных не открываются

#### Scenario: Покрытие основных состояний
- **WHEN** проверяется состав тестов
- **THEN** покрыты поиск, выбор кандидата, поиск записи сайта, сохранение связи, ошибки backend, обновление списка и пустые состояния

### Requirement: Документация проекта описывает запуск фронтенда
Корневой `README.md` SHALL содержать раздел о фронтенде с командами локального запуска и указанием порта, а контекст проекта в `openspec/config.yaml` и корневой `AGENTS.md` SHALL упоминать frontend-папку и её правила минимальными согласованными правками.

#### Scenario: README объясняет запуск
- **WHEN** читатель открывает README
- **THEN** он находит команду локального запуска фронтенда и порт, на котором открывается приложение

#### Scenario: Контекст проекта обновлён
- **WHEN** проверяются `openspec/config.yaml` и корневой `AGENTS.md`
- **THEN** в них есть краткое упоминание папки `frontend/` и её роли, без дублирования уже имеющихся разделов
