# Spec Delta

## Purpose

Безопасное сохранение связи требует актуальных исходных записей, явного решения сотрудника и минимального аудита, сохраняя уникальность идентификаторов при конкуренции.

## ADDED Requirements

### Requirement: Подтверждение расхождений
Система SHALL сохранять requires_confirmation пару только с актуальным assessment token, confirmed=true и причиной длиной 1–1000 Unicode символов после trim. Blocked SHALL NOT обходиться подтверждением.

#### Scenario: Нет подтверждения
- **WHEN** пара требует подтверждения, а token, confirmed=true или непустая причина отсутствуют
- **THEN** связь не создаётся, возвращается confirmation_required либо invalid_confirmation

#### Scenario: Корректное ручное решение
- **WHEN** сотрудник подтверждает актуальные расхождения с допустимой причиной
- **THEN** связь сохраняется вместе с фактом подтверждения, причиной, временем и структурированными кодами расхождений

### Requirement: Повторная проверка перед сохранением
Backend SHALL повторно получить обе записи и пересчитать оценку перед каждой записью связи. Для ready допускается существующий запрос с двумя ID без токена; наличие переданного токена SHALL всегда проверяться.

#### Scenario: Совместимый готовый запрос
- **WHEN** существующий клиент передаёт только два ID и свежая оценка ready
- **THEN** создаётся связь без ручной причины с прежним успешным форматом ответа

#### Scenario: Данные изменились после оценки
- **WHEN** пересчитанная оценка или исходные поля отличаются от подтверждённого токена
- **THEN** возвращается assessment_stale без создания связи, даже если новые данные стали ready

### Requirement: Уникальность и атомарный аудит
Система SHALL сохранять связь и аудит одним атомарным действием и обеспечивать уникальность каждого CRM ID и Site ID средствами собственной PostgreSQL. Аудит SHALL NOT копировать исходные ФИО и даты; идентификатор сотрудника откладывается до авторизации.

#### Scenario: Конкурентное создание
- **WHEN** два запроса одновременно занимают один CRM ID или Site ID
- **THEN** максимум один успешно сохраняется, другой получает конфликт; частичного аудита или связи не остаётся

#### Scenario: Ошибка аудита
- **WHEN** сохранение данных ручного решения завершается ошибкой
- **THEN** связь также не сохраняется

### Requirement: Контракт и безопасные ошибки
Assessment и создание SHALL документироваться в backend OpenAPI; поиск, CSV export, идентификаторы string и существующие поля успешного ответа связи SHALL сохраняться. Ошибки SHALL NOT раскрывать SQL, токены или исходные персональные поля.

#### Scenario: Описание нового сценария
- **WHEN** потребитель читает OpenAPI
- **THEN** POST /api/v1/link-assessments и расширенный POST /api/v1/links описывают nullable birthday, статусы, причины, токен и ошибки, соответствующие фактическим DTO
