# Design

## Context

Ветка feat/crm-name-search на c6a330aa4f9f5b8dd63bd453470eb75cc57b8dbf. Stage 0–3 завершены. Следуют Stage 4 Bitrix24 Adapter, Stage 5 Search HTTP API, Stage 6 Frontend и Stage 7 подготовка к эксплуатации. Источники решений — два Explore и уточнения владельца к Propose.

- **Код проекта.** `CRMReader` принимает `Search(ctx, query, limit)` и `GetByID(ctx, id string)`. `ClientSearchService` запрашивает до 50 кандидатов. CSV индексирует записи и сортирует по баллу, нормализованному имени и строковому ID. `Assess` и `CreateLink` вызывают `readCRM → GetByID`. Хранилище обеспечивает уникальность точной строки `crm_id`. [Порт](../../../backend/internal/application/ports/crm_reader.go) · [Поиск](../../../backend/internal/application/services/client_search.go) · [Assessment](../../../backend/internal/application/services/assessment.go) · [Сохранение](../../../backend/internal/application/services/client_link.go)
- **Код Site.** Общий `site/shared.ParseTitle` оставляет одно слово в `UnstructuredName`, для двух и более слов присваивает первое `ShortName`, остальные объединяет в `LastName`. Site-представление для сравнения — `UnstructuredName` либо `ShortName + LastName`. Отдельной роли отчества нет. Текущий `matcher.Assess` сравнивает фамилию, имя и дату, а при `UnstructuredName` обнуляет обе роли соответствующего источника. ## Goals / Non-Goals

Сохранить границы Ports & Adapters, порт чтения и действующие формы HTTP-ответов. Выполнять только серверно отфильтрованное чтение CRM и передавать в Domain собственные сущности. Границы Stage 4 перечислены в [proposal](proposal.md).

## Domain Concepts

| Понятие | Значение и ограничения |
|---|---|
| Идентичность карточки CRM | Положительный ID из диапазона int64 для Bitrix, каноническая десятичная строка в `CRMClient.ID`, портах, токене и OD. `b24.ID` принадлежит транспортному DTO. CSV сохраняет свои строковые ID. |
| Авторитетное полное имя CRM | `SourceFullName` хранит исходный `title` целиком. Пустое значение, null и строка только из пробелов означают отсутствие авторитетного имени. Присутствующий title определяет отображение и слова CRM для сравнения. |
| Вспомогательная роль CRM | Фамилия, имя и отчество хранятся отдельно с исходными значениями. При заполненном title роль получает подтверждение из точного совпадения целых нормализованных слов title. При пустом title известные компоненты образуют резервное представление. |
| Представление Site | Известные роли `ShortName` и `LastName` из действующего адаптера, либо целая строка с неизвестными ролями. Неизвестное отчество Site допустимо. |
| Поисковое представление | Слова авторитетного имени, при его отсутствии — слова резервного представления. Подтверждённая роль имени может аннотировать существующие слова для Stage 0. Серверное совпадение по вспомогательному полю только доставляет кандидата. |
| Оценка пары и её снимок | Текущие три проверки `last_name`, `first_name`, `birthday`. Доказательство согласия имени имеет отдельные правила от поиска кандидата. Снимок привязан к ID, исходному title, компонентам, датам и версии assessment-правил. |
| Дата рождения | Календарная дата `client.Date` или отсутствие. Часовой пояс строки источника не меняет её календарный день. |
| Завершённая выборка | Все страницы каждого запущенного фильтра прочитаны. Предел числа кандидатов применяется к локальному рейтингу. Совпадения, пропущенные серверным фильтром или незапущенным опциональным расширением, относятся к полноте поиска, а исчерпание бюджета начатой выборки — к ошибкам операции. |

## Decisions

### SDK и граница адаптера

Владелец подтвердил процесс «Дети» на `bitrix.podari-zhizn.ru`, `entityTypeId=135`, внутренний ID типа 6 и около 25 121 карточки на момент исследования. Хост задаётся конфигурацией. Во всех вызовах используется `135`. Классический REST и JSON POST выполняет SDK, который дописывает `.json` к имени метода. Выбираем `github.com/bitrix24/b24gosdk v0.2.0`, Go 1.21+, MIT, без транзитивных модулей по go.mod. SDK создаётся один раз в outbound adapter и используется параллельными запросами. Для каждого поиска создаётся собственный pager. Адаптер строит параметры и DTO, маппит данные и ошибки, управляет бюджетом. [SDK client](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/client.go) · [Модуль](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/go.mod) · [Версия](https://github.com/bitrix24/b24gosdk/tree/v0.2.0)

Владелец осознанно выбрал классические `crm.item.list` и `crm.item.get` для подстрочного поиска с оператором `%`. Bitrix24 помечает оба метода как deprecated. Миграция на REST 3.0 потребует отдельной проверки эквивалентности поиска. [List](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html) · [Get](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-get.html)

### Транспорт и свежая карточка

| Поле | Маппинг |
|---|---|
| `id` | `b24.ID` → положительное значение → `.String()` |
| `title` | `SourceFullName` |
| `ufCrm7_1657182997586` | `LastName` |
| `ufCrm7_1656048402` | `FirstName` |
| `ufCrm7_1656048409` | `Patronymic` |
| `ufCrm7_1656048422` | `Birthday` |


a. `crm.item.list` передаёт ровно эти шесть camelCase-ключей в `select`. `Pages` читает `result.items`, объявленный в профиле семейства `crm.item`. Отсутствующий или неверно типизированный массив обрабатывается как ошибка SDK, `items:null` SDK поддерживает как пустой список. `useOriginalUfNames` опускается.

b. `GetByID` проверяет, что вход совпадает с канонической десятичной записью положительного int64. Например, `00123`, `+123`, `0` и переполнение отвергаются до I/O. Использовать доменную sentinel для неверного CRM ID и преобразовать её в действующий `services.ErrInvalidID` в `readCRM`. Сервисы уже обрезают внешние пробелы, допустимая строка после trim является ключом проверки и записи. Это закрывает обход уникальности через альтернативное написание ID и сохраняет текущее поведение CSV.

c. `CallJSON(ctx, "crm.item.get", params, WithIdempotent(), WithTimeout(...))` отправляет `entityTypeId` и числовой `id`. `result.item` обязателен, ID ответа должен совпасть с запросом. Тот же DTO и маппер применяются к строкам списка и карточке. `get` не имеет документированного `select`. Декодируем нужные поля, оставляем `Clinic` пустым, вспомогательных запросов к CRM нет. Положительные числовые и строковые ID ответа допускаются. Нулевые, отрицательные, отсутствующие ID и значения, которые `b24.ID` не декодирует, означают ошибку данных источника. [List](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html) · [Get](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-get.html) · [SDK ID](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/id.go)

Дата — `YYYY-MM-DD` либо наблюдавшийся RFC3339 timestamp со смещением. Проверить форму timestamp целиком, извлечь десять первых символов исходной строки и передать в `client.ParseDate`. Например, `2006-04-16T03:00:00+04:00` остаётся `2006-04-16`. Отсутствие поля, null и пустая строка дают nil. Непустое некорректное значение, включая невозможную дату и неверный JSON-тип, означает ошибку данных. Отбор по дате и смена её семантики в Site вне этого дизайна. [Типы Bitrix](https://apidocs.bitrix24.ru/api-reference/data-types.html) · [Календарная дата](../../../backend/internal/domain/client/birthday.go)

### Приоритет title в поиске и оценке

`CRMClient.FullName()` проверяет наличие `SourceFullName` и возвращает исходную строку. При отсутствии действует нынешний путь `UnstructuredName` или сборки из известных компонентов. DTO выдаёт то же `full_name` и исходные структурированные поля в существующих ключах. Заменять пробелы или назначать роли в исходной строке для отображения не требуется.

Для проверки вспомогательной роли использовать `NormalizeName` и первичные формы слов текущей токенизации. Искомые слова роли должны занимать непрерывный диапазон слов title. `Иван` внутри `Иванов`, алиас, префикс, подстрока, опечатка и подмена алфавита не подтверждают роль. Для проектной версии подтверждаем только роль с единственным таким диапазоном. Если диапазоны двух подтверждаемых ролей пересекаются, обе роли считаются неопределёнными. Так один и тот же фрагмент не получает две разные роли. Составное значение сравнивается как последовательность, с текущими границами слов, включая дефис.

`TokenizeCRMName` при наличии title выдаёт слова title один раз. Слова в подтверждённом диапазоне `FirstName` получают текущую аннотацию given-name и формы алиасов. Все прочие сохраняют роль неизвестной. Сохраняем `MatchNameTokens`, веса и правила Stage 0 без переписывания. Результаты с баллом 0 исключаются. При пустом title сохраняется существующая токенизация. [Токенизация](../../../backend/internal/domain/client/name_search.go) · [Нормализация](../../../backend/internal/domain/client/name.go)

**Правило assessment.** Поисковый балл Stage 0 применяется только к выдаче. При отсутствующем title действуют текущие проверки компонентов. Для Site с `UnstructuredName` обе роли остаются `missing` даже при совпадении полных строк.

1. Для каждой известной роли Site искать в title единственный непрерывный диапазон целых слов, совпадающий с основными нормализованными токенами роли. Это прямое доказательство из title независимо от UF и позиции. Если прямого диапазона нет, для этой роли использовать подтверждённый диапазон соответствующего UF. Повторы одинакового диапазона в разных позициях делают прямое доказательство неоднозначным. Одно и то же слово нельзя засчитать дважды. При пересечении прямого диапазона и диапазона из UF сохранять прямой, конкурирующую роль считать неизвестной. При пересечении двух диапазонов одного уровня обе роли считать неизвестными. Если фамилия установлена, а для известного имени Site нет прямого диапазона и подтверждённого диапазона UF, искать среди оставшихся слов единственный непрерывный диапазон, который даёт `alias_match` по текущему правилу имени. При нескольких таких диапазонах имя остаётся неизвестным. Алиас не определяет диапазон фамилии. Порядок слов title роли не задаёт.
2. Для каждой установленной роли отдельно применить действующий `compareName` к исходному фрагменту title и значению Site. Одинаковые исходные строки дают `exact`, равенство после `NormalizeName` даёт `normalized_match`, известный Stage 0 алиас имени даёт `alias_match` только для `first_name`, действующее правило допустимой опечатки или смешения алфавитов даёт `probable_match`, установленная роль без совпадения даёт `mismatch`, а неизвестная или пустая роль даёт `missing`. Для прямого диапазона, полученного по основным токенам, при различиях только в границах или разделителях токенов использовать `normalized_match`. `crm_value` роли берётся из соответствующего фрагмента title. При полном покрытии двумя прямыми диапазонами конфликтующие UF сохраняются в карточке, а их значения не участвуют в оценке. При равных датах эта пара имеет статус `ready`.
3. Проверять остаток title после разметки имени и фамилии, когда обе роли установлены, не пересекаются и имеют `exact`, `normalized_match`, `alias_match` или `probable_match`. Пустой остаток согласован независимо от UF отчества. Ровно одно оставшееся слово считается объяснённым, если оно подтверждено UF Patronymic ИЛИ распознано консервативным суффиксным правилом. Для подтверждения через UF слово должно целиком совпасть с единственным нормализованным словом непустого UF отчества, диапазон которого однозначен и не пересекается с именем и фамилией. Для суффиксного распознавания слово должно быть целым фрагментом исходной строки, ограниченным пробелами или границами строки. После `NormalizeName` оно должно состоять только из букв `а–я`, иметь минимум две буквы перед одним из окончаний `ович`, `евич`, `овна`, `евна`, `ична` (выбирать самое длинное подходящее окончание). Токенизация Stage 0 помогает определить границы, а словарь алиасов не определяет отчества. Суффиксное правило действует при любом значении UF. Несовпадающее UF не отменяет успешное распознавание и сохраняется в исходном виде. Одно слово, которое не прошло ни одну из двух проверок, или несколько оставшихся слов дают общую несогласованность title и требуют подтверждения. Причина — необъяснённый остаток авторитетного title. Отчество Site не восстанавливается. Когда роль уже имеет `missing` или `mismatch`, она сама требует подтверждения.
4. Сохранять фактические результаты трёх доменных проверок. Общая несогласованность title из пункта 3 учитывается отдельно в `requires_confirmation` и добавляет существующий аудиторский код `name:mismatch` с обычной дедупликацией. `alias_match` и `probable_match` сохраняют свои коды и также требуют подтверждения. Для `ready` нужны три проверки с `exact` или `normalized_match` и согласованное покрытие title, если он присутствует.
5. HTTP handler только при общей несогласованности title отображает её в существующей позиции `field=last_name, code=mismatch`. Это ограничение действующего HTTP-контракта. Фактическая проверка фамилии в домене сохраняет свой результат. В `crm_value` этой позиции передаётся полный исходный CRM title, в `site_value` — полное представление Site, доступное в домене (`ShortName + LastName` либо `UnstructuredName`). Порядок, поля, коды и OpenAPI сохраняются. В Stage 6 интерфейс должен показывать оба полных значения ФИО и описывать эту причину как расхождение ФИО, без вывода о фамилии по одному коду.

### Серверный отбор и общий бюджет

1. Взять токены исходного запроса из Stage 0. При отсутствии токенов или `limit <= 0` вернуть пустую выдачу без I/O. Для основного фильтра использовать первичные токены, исходные формы с `ё` и канонические формы с `е`, доступные однозначные формы смешанных алфавитов и известные алиасы только по полю имени и title для обнаружения карточки. Для выдачи алиас применим по текущему правилу Stage 0 и подтверждённой роли. Дедуплицировать пары поле/значение. Не раздувать варианты комбинаторно. Ввести предел числа условий на один запрос. Слишком широкий основной фильтр завершается безопасной ошибкой до I/O, токены запроса не отбрасываются молча.
2. Один `crm.item.list` pager на основной фильтр. Один OR содержит дочерний объект на каждую пару поле/значение. Пример формы `{"filter":{"0":{"logic":"OR","0":{"%title":"Иванов"},"1":{"%ufCrm7_1657182997586":"Иванов"}}}}`. Тот же оператор применяется к имени и отчеству. В значение символ `%` не добавляется. Документация подтверждает `logic: "OR"` с числовыми ключами, владелец подтвердил `%` для UF фамилии. Комбинация со всеми полями, collation и стабильное `order: {"id":"ASC"}` требуют проверки портала. Соседние предикаты верхнего уровня соединяются через AND. В Stage 4 дополнительные предикаты даты отсутствуют. Если реальный портал окажется несовместим с общей OR-группой, раздельные серверные выборки по полям возможны как отдельная правка плана с тем же общим бюджетом. [Синтаксис list](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html)
3. После полного основного отбора и локальной оценки опционально запустить не более одного дополнительного фильтра. Начальный эксперимент — запуск при нуле положительных баллов, наличии длинного токена и резерва для завершения выборки. Взять самый длинный токен с длиной от пяти рун (при равенстве первый), разделить на два непересекающихся фрагмента, каждый не короче двух рун, и искать фрагменты по тем же полям через OR. Это исследовательский вариант для синтетического сравнения с базой. Выбранные фрагменты могут дать широкую выборку или пропустить перестановку на их границе. Включение расширения зависит от замеров, до подтверждения пользы оно выключено в production. Если оно уже началось, его сбой или обрезание делает весь поиск ошибкой. При многословном запросе точный токен часто даёт кандидату попасть в базовую выборку и получить балл за опечатку другого слова. Гарантии полного восстановления опечаток нет.
4. Последовательно обходить `Core().Pages("crm.item.list", params, WithCallOptions(WithTimeout(...)))`. SDK знает путь `items` и автоматически ставит идемпотентность. Перед каждым `Next(ctx)` проверять общий deadline и остаток страниц. После успеха прочитать `p.Page().Next`, считать каждую полученную страницу, включая пустую. Для offset-пагинации от нуля при наличии указателя требовать значение строго больше предыдущего запрошенного offset. SDK отслеживает только часть циклов. Нулевой, отрицательный и регрессирующий offset в этом протоколе — техническая ошибка. При `Next == nil` текущий фильтр завершён, при известном продолжении после последней разрешённой страницы сразу вернуть ошибку без ещё одного запроса. При `Next(ctx) == false` проверить `Pager.Err()`. `Take` ограничивает строки, а `Scan` теряет подтверждённый индикатор продолжения и использует другой курсор. [Pager SDK](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/pager.go)
5. SDK `v0.2.0` сводит отсутствующий, null и неразбираемый `next` к nil. Адаптер гарантирует проверку полученного указателя и продвижение распознанного offset. Для повреждённого сырого поля общей гарантии нет. `total` годится для наблюдения, но не доказывает полноту при изменениях данных. SDK не отдаёт сырой envelope, поэтому самостоятельный парсер и замена SDK оставляются за рамками без подтверждения несовместимости. Подтвердить формат `next` и завершение до эксплуатации. Offset не обеспечивает снимок. Порядок по ID и дедупликация уменьшают последствия, пропуски при смене набора возможны. [Парсинг SDK](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/internal/rest/client.go#L362)
6. Декодировать и дедуплицировать по каноническому ID между страницами и выборками, при повторе сохранять первую успешно прочитанную версию. Любое обнаруженное повреждение строки технически завершает выборку ошибкой. Сортировать положительные баллы по убыванию, затем по `NormalizeName(FullName())` и строковому ID как CSV. Применять `limit` после сортировки. Проверять deadline при маппинге, ранжировании и до возврата, включая случай, когда страницы уже прочитаны. Исчерпание бюджета при оставшихся страницах, отмена и ошибки не возвращают частичный результат.

Бюджеты живут в политике адаптера с тестовым переопределением. Исходная retry-политика — `WithRetry(RetryConfig{MaxAttempts:1})`, поэтому одна логическая страница требует не более одного HTTP-вызова. Размер страницы до 50, число фильтров 1 в базовом пути и до 2 в эксперименте. В Apply выбрать и обосновать консервативные предварительные пределы условий, страниц и времени по синтетическим сценариям, с запасом до `WriteTimeout=30s`. Отдельно записать число REST-попыток, число страниц, локальное время декодирования и рейтинга, полное время (p50/p95) и долю восстановления известных опечаток (найдено / размечено), сравнить базу и расширение на одинаковом наборе. Добавить профиль запроса «Иванов» на большом синтетическом наборе с совпадениями в каждом из четырёх полей. Измерить размер выборки, страницы, попытки и задержку OR-фильтра при завершении выборки и исчерпании бюджета. При известном продолжении проверить ошибку без частичного top-50. Синтетические показатели обосновывают защиту процесса, а эксплуатационные значения и включение fuzzy-расширения требуют последующей проверки задержек и квот на разрешённом окружении.

### Ошибки, контекст и секрет

- Использовать `WithHTTPClient` с одним стандартным клиентом, переиспользованием соединений, таймаутом одной попытки и `CheckRedirect`, запрещающим переходы. Ограничить объём тела до `io.ReadAll` SDK при необходимости защиты памяти. Для этого достаточно небольшой обёртки стандартного транспорта, возвращающей ошибку при превышении первого лишнего байта. Транспорт не формирует REST-запросы и не разбирает envelope. `WithTimeout` ограничивает одну операцию SDK с потенциальным backoff. Внешний контекст ограничивает весь поиск, отмена распространяется до HTTP и локальных циклов. Встроенные повторы SDK можно включить лишь после оценки бюджета. `Pages` сам отмечает чтение как идемпотентное, `GetByID` делает это через `WithIdempotent`. SDK при включённых повторах повторяет `QUERY_LIMIT_EXCEEDED` и ряд неоднозначных сетевых сбоев для идемпотентного вызова. `429 OPERATION_TIME_LIMIT`, credentials и права требуют контролируемой ошибки. Второй слой повторов не нужен. [Call options](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/core.go#L194) · [Retry](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/internal/rest/client.go#L185)
- `errors.As` и `errors.Is` с кодами SDK применяются внутри адаптера. `*APIError.Error()` может содержать описание или сырое тело, внешняя транспортная ошибка может содержать URL. Наружу возвращать только безопасную классификацию с сохранением `errors.Is` для отмены, таймаута и доменных sentinel errors. `CodeOf` допустим для распознавания, в журнал выводятся только известные коды, безопасные имена методов, счётчики и времена. SDK на 2xx не распознаёт пустой `error` как ошибку, поэтому валидировать контракт `items` или `item`. [SDK errors](https://github.com/bitrix24/b24gosdk/blob/v0.2.0/errors.go)
- `NOT_FOUND` документирован и для записи, и для процесса. В Stage 4 один этот код всегда даёт техническую ошибку. Преобразование ответа Bitrix в `client.ErrCRMNotFound` отложено до достоверного подтверждения однозначного признака на реальном портале. Действующее поведение CSV сохраняется. Ошибка HTTP 404, права и неверный ID ответа не доказывают отсутствие карточки. Ошибку данных в `GetByID` возвращать через `client.ErrInvalidSourceData`. В `Search` неверные данные или исчерпанный лимит страниц возвращать через безопасную техническую ошибку существующего mapping, отмену или истечение времени — по действующим sentinel. Так сохраняются текущие 500/499/504 поиска и действующие 502 оценки. [Get](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-get.html) · [Mapping](../../../backend/internal/adapters/inbound/http/handlers/response.go)
- До создания SDK проверять HTTPS, непустой хост, путь ровно `/rest/<положительный user_id>/<непустой secret>/`. Запретить userinfo, query, fragment, percent-кодированные и неоднозначные сегменты, а также `/rest/api/`. Ошибка содержит только имя переменной и безопасную причину. Полный URL хранится как секрет, не печатается и не доступен в диагностике SDK. Образ и frontend не получают переменную. Тесты используют фиктивный webhook. Gin уже исключает query string. До подключения реальных данных требуется проверить access logs Nginx и других ingress-прокси, поскольку текущий GET несёт `q` в URL. Эта эксплуатационная проверка не меняет frontend и маршруты в Stage 4. [Вебхуки](https://apidocs.bitrix24.ru/first-steps/first-rest-api-call.html) · [Gin](../../../backend/internal/adapters/inbound/http/router.go) · [Nginx](../../../frontend/nginx.conf)

### Wiring и тестовые границы

`config.Load` валидирует только выбранный CRM-режим. `CRM_SOURCE` по умолчанию `csv` с обязательным `CRM_PATH`. Для `bitrix24` обязателен `BITRIX24_WEBHOOK_URL`. Неизвестный режим или неверная обязательная настройка останавливает запуск. Composition root строит один `ports.CRMReader` и передаёт его обоим сервисам. После выбора backend возвращает сбой Bitrix как техническую ошибку без переключения. `/healthz` сохраняет проверку OD. Локальный Compose явно выбирает CSV с существующим mount, production явно выбирает Bitrix, удаляет CSV-параметр и mount. Секрет передаётся только backend из защищённого окружения или файла вне репозитория, без вывода интерполированного Compose или окружения контейнера.

В адаптере предусмотреть точку внедрения уже созданного `*b24.Client` для wire-тестов с `b24test.Portal.Client(...)` и для сквозных тестов через `ports.CRMReader`. `Portal.URL()` использует HTTP, поскольку fake portal поднимается через `httptest.NewServer`. Production wiring создаёт SDK-клиент после штатной валидации HTTPS и webhook. Отдельно проверить отказ для HTTP URL и штатный путь с TLS через `httptest.NewTLSServer` с доверенным тестовым HTTP-клиентом.

`b24test.NewPortal` проверяет запросы и ответы, `WrappedListResult("items", ...)` — страницы, `Result` — `item`, `OnError` — известные ошибки. `CallsTo` проверяет параметры и число вызовов. Fake portal повторяет последний ответ, поэтому тесты явно проверяют число попыток и остановку. Для TLS и редиректов, нестандартных статусов, задержек и обрыва дополнить штатным `httptest` с реальным SDK. Синтетические fixtures покрывают DTO, даты и модель имени. [b24test](https://github.com/bitrix24/b24gosdk/tree/v0.2.0/b24test)

## Risks / Trade-offs

- Серверная фильтрация ограничивает полноту поиска. Критерии опечаток измеряются отдельно от работоспособности базовой выборки.
- Полное покрытие без учёта лишних слов дало бы ложный ready. Проверки диапазонов и ограниченное распознавание отчества учитывают остаток. Суффиксное правило покрывает только заданные формы. Некоторые отчества потребуют подтверждения. Неизвестные роли и непокрытые слова увеличивают ручное подтверждение.
- Некорректный сырой cursor может быть неразличим с концом списка в SDK. На синтетике проверяем это ограничение, на портале сверяем форму метаданных.
- Scope `crm` и права пользователя вебхука на процесс и отдельные поля нужны для чтения. Bitrix24 может молча игнорировать `filter` или `order` по закрытым полям. Это может расширить выборку и исчерпать бюджет либо нарушить ожидаемый порядок страниц. На портале предстоит подтвердить доступность всех ключей `select`, четырёх полей OR и `id` для сортировки. Проверить, что каждое условие по отдельности и общий OR ограничивают выборку, а порядок по ID действует. [List](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html)

## Migration Plan

Существующие связи демонстрационные. Для будущей production-проверки предоставить отдельную чистую OD и применить штатные миграции. Смена режима с общей OD означает смену пространства значений `crm_id`. Возврат к локальному CSV выполняется явной конфигурацией с демонстрационной OD. Никакой очистки, переноса данных или изменения схемы. Перед эксплуатацией проверить ingress-логи, права и совместимость фильтра в отдельно разрешённом окружении.

## Open Questions

- Codex выбирает предварительную политику бюджета по синтетическим замерам и фиксирует точные ограничения SDK в отчёте Verify.
- Для будущей разрешённой проверки остаются комбинированный OR с процентным оператором, collation, стабильность ID-order, формат метаданных страниц и пустых UF, права на поля и фактическое действие filter/order, однозначный признак отсутствия карточки, реальные квоты и задержка. Синтетические проверки не зависят от доступа к порталу.
