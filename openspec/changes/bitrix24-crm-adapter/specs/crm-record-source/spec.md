# Spec Delta

## Purpose

Предоставить поиск кандидатов и актуальное чтение карточек CRM для оценки пары и создания связи. Поддержать Bitrix24 в production и синтетический CSV для локальной работы.

## ADDED Requirements

### Requirement: Явный выбор CRM-источника
Приложение SHALL выбирать один источник на запуск и требовать настройки выбранного режима. Локальный default SHALL быть CSV, production Compose SHALL явно выбирать Bitrix24.

#### Scenario: Локальная демонстрация
- **WHEN** режим отсутствует или выбран `csv` и задан `CRM_PATH`
- **THEN** поиск и чтение работают на CSV без настроек Bitrix24

#### Scenario: Production
- **WHEN** выбран `bitrix24`
- **THEN** требуется корректный `BITRIX24_WEBHOOK_URL`, CSV-файл не требуется и сбой CRM возвращается как ошибка без перехода на CSV

#### Scenario: Ошибка конфигурации
- **WHEN** задан неизвестный режим или настройка выбранного источника отсутствует либо некорректна
- **THEN** сервер завершает запуск с безопасной ошибкой

### Requirement: Авторитетное полное имя и отдельные компоненты
Bitrix-источник SHALL хранить исходный `title` и доступные компоненты независимо. Заполненный `title` SHALL определять полное отображаемое имя. Структурированная роль при наличии `title` SHALL подтверждаться только по целым нормализованным словам.

#### Scenario: Противоречие или подстрока
- **WHEN** `title` содержит «Иванов», а структурированное имя равно «Иван» и отдельного слова «Иван» в строке нет
- **THEN** оба исходных значения сохраняются, полное имя берётся из `title`, значение «Иван» не подтверждается как роль и не даёт самостоятельного балла ранжирования

#### Scenario: Отсутствуют поля имени
- **WHEN** `title` пуст либо отсутствует, а заполнена только часть компонентов
- **THEN** доступные компоненты образуют неполное имя и карточка читается по ID. Карточка без всех полей имени также доступна по ID при корректных остальных данных

### Requirement: Поиск кандидатов в Bitrix24
Bitrix-источник SHALL выполнять серверный отбор по любому из четырёх полей имени и локально ранжировать полученных кандидатов по Stage 0 с учётом авторитетного имени. Выдача SHALL содержать уникальные ID и иметь стабильный порядок для одного и того же набора данных.

#### Scenario: Слова в разном порядке и полях
- **WHEN** серверный фильтр находит карточку по одному из слов запроса и авторитетное имя локально соответствует словам запроса в произвольном порядке
- **THEN** карточка участвует в общем ранжировании независимо от порядка слов и поля, которое позволило её получить

#### Scenario: Повтор карточки или лучший кандидат на поздней странице
- **WHEN** один ID пришёл несколько раз и лучший кандидат находится после первой страницы
- **THEN** каждый ID участвует один раз, а выходной лимит применяется после ранжирования всех страниц завершённых выборок

#### Scenario: Карточка не найдена серверным фильтром
- **WHEN** локальное правило могло бы сопоставить опечатку, но серверный фильтр не вернул карточку
- **THEN** выдача может не содержать такую карточку, а запрос не приводит к чтению всего справочника

### Requirement: Полнота запущенных выборок в пределах бюджета
Bitrix-источник SHALL ограничивать время всей операции поиска и суммарное число страниц начатых выборок. Если бюджет исчерпан при наличии продолжения или чтение начатой выборки прервалось, результат SHALL быть технической ошибкой без карточек.

#### Scenario: Последняя разрешённая страница
- **WHEN** на последней разрешённой странице CRM сообщает о продолжении
- **THEN** источник завершает запрос ошибкой без дополнительной страницы и без частичной выдачи

#### Scenario: Широкая выборка по частой фамилии
- **WHEN** OR по четырём полям для «Иванов» исчерпывает бюджет при известном продолжении
- **THEN** источник возвращает техническую ошибку без частичного top-50 и без следующего запроса

#### Scenario: Страница завершает выборку ровно на лимите
- **WHEN** последняя разрешённая страница завершает все начатые выборки и операция укладывается во время
- **THEN** источник возвращает ранжированную выдачу, ограниченную запрошенным числом кандидатов

#### Scenario: Ошибка дополнительной выборки
- **WHEN** дополнительная выборка для опечаток уже началась и завершилась ошибкой, таймаутом или обнаруженным сбоем курсора
- **THEN** источник возвращает ошибку без выдачи из предыдущих страниц или базовой выборки

### Requirement: Актуальная карточка по каноническому ID
Bitrix-источник SHALL читать карточку по положительному каноническому десятичному ID при каждом вызове получения по ID. Доменный ID SHALL оставаться строкой.

#### Scenario: Различное представление в ответе
- **WHEN** CRM возвращает ID числом или десятичной строкой
- **THEN** источник возвращает его каноническую строку. Для чтения по ID значение ответа должно совпасть с запросом

#### Scenario: Неканонический вход
- **WHEN** передан ID вида `00123`, неположительное число или число вне диапазона int64
- **THEN** источник возвращает ошибку недопустимого ID до сетевого запроса

#### Scenario: Неоднозначное отсутствие карточки
- **WHEN** Bitrix24 возвращает `NOT_FOUND`, HTTP 404 либо ошибку доступа при чтении карточки
- **THEN** источник возвращает безопасную техническую ошибку. Для Bitrix24 поддержка `client.ErrCRMNotFound` отложена до достоверного подтверждения на реальном портале признака отсутствия именно карточки

### Requirement: Календарная дата CRM
Дата рождения SHALL сохраняться как календарная дата из исходного значения. Пропуск, null и пустая строка SHALL обозначать отсутствие даты. Непустая некорректная дата SHALL считаться ошибкой данных источника.

#### Scenario: Дата со смещением
- **WHEN** источник возвращает `2006-04-16T03:00:00+04:00` либо `2006-04-16`
- **THEN** доменное значение равно `2006-04-16`

#### Scenario: Невозможная календарная дата
- **WHEN** входное поле содержит `2023-02-29`
- **THEN** чтение завершается безопасной ошибкой источника без результата

### Requirement: Безопасность и отмена чтения CRM
Bitrix-источник SHALL использовать HTTPS с полным секретным URL классического входящего webhook. Ошибки и журналы SHALL исключать этот URL, исходные тела ответов и клиентские значения. Отмена и таймаут SHALL различаться.

#### Scenario: HTTP URL в production-конфигурации
- **WHEN** URL выбранного Bitrix24 webhook использует HTTP
- **THEN** запуск завершается безопасной ошибкой конфигурации до создания SDK-клиента

#### Scenario: Сбой транспорта или отказ Bitrix
- **WHEN** ответ или транспортная ошибка содержит URL, ФИО или дату рождения
- **THEN** наружу попадает безопасная классификация без исходных значений и сырых ошибок SDK

#### Scenario: Отмена между страницами
- **WHEN** вызывающий отменяет контекст до следующей страницы
- **THEN** новые страницы не запрашиваются, выдача отсутствует, `errors.Is` распознаёт отмену
