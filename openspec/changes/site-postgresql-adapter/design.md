# Design

## Context

Stage 1 завершён. Текущий SiteReader читает CSV, внутренние Site ID строковые, а собственная БД хранит связи в client_links.site_id TEXT. Сервисы просмотра, assessment и создания связи используют один SiteReader. См. proposal.md.

## Goals / Non-Goals

**Goals:** единая числовая идентичность сайта во всех внутренних слоях, совместимый HTTP-формат, изолированное чтение источника и атомарная смена типа в БД связей.

**Non-Goals:** границы этапа определены в proposal.md.

## Domain Concepts

- Site ID идентифицирует строку public.children по первичному ключу id. Внутренний тип int64 во всём знаковом диапазоне BIGINT. Значение 0 остаётся допустимым для lookup и при отсутствии строки даёт существующий not found. CRM ID остаётся строкой.
- Дата рождения представлена календарной датой client.Date с годами 1–9999. NULL означает отсутствие сведений. Неподдерживаемая дата блокирует чтение, оценку и сохранение.
- Связь CRM и сайта уникальна по каждому из независимых ключей. Assessment token относится к конкретной паре, снимку данных и версии правил.

## Decisions

1. **Сквозной тип.** SiteClient.ID, ClientLink.SiteID, Decision.SiteID, SiteReader.GetByID, ClientLinkRepo.LookupBySourceIDs, методы просмотра/оценки/сохранения, TokenClaims.SiteID и Verify получают int64. pgx передаёт и сканирует int64 без текстовых преобразований. Прежние строковые типы остаются в транспортных DTO. HTTP использует одну функцию разбора path и обоих тел: TrimSpace, затем strconv.ParseInt(s, 10, 64). Допустимы знак и ведущие нули, запрещены дроби, экспонента, префиксы и переполнение. JSON-число и отсутствующее обязательное поле сохраняют существующий binding-ответ invalid_body. При корректном binding недопустимая строка даёт 400 invalid_id перед вызовом сервиса. Выходные site_id, id карточки и CSV export используют strconv.FormatInt(id, 10). OpenAPI сохраняет string и описывает ошибки и допустимый диапазон.
2. **Токен.** TokenVersion повышается до 2. Signed payload использует типизированное JSON-число int64, проверяемое на Go backend без промежуточного float64. Клиент передаёт токен как opaque string. Fingerprint сохраняет length-prefix сериализацию и маркеры nullable-полей, используя канонический десятичный Site ID. Сохраняются HMAC с раздельными ключами подписи и fingerprint, TTL, повторное чтение и проверка правил. Прежний формат отклоняется как invalid_assessment_token. Эквивалентные входные записи ключа попадают в одну запись и один unique constraint.
3. **Чтение сайта.** Один параметризованный pgx SELECT id, title, ((birthday AT TIME ZONE 'UTC') AT TIME ZONE 'Europe/Moscow')::date FROM public.children WHERE id = $1. Для SQL date использовать nullable pgtype.Date, проверять infinity и client.Date.IsValid. Ошибку диапазона при SQL-преобразовании даты в этом запросе классифицировать как client.ErrInvalidSourceData (в частности SQLSTATE 22008), иные SQL/scan ошибки считать техническими. Учитывать отмену/таймаут с сохранением errors.Is, pgx.ErrNoRows отображать в client.ErrSiteNotFound. Существующий HTTP mapping даёт 502 для invalid source, текущие 404 или blocked для отсутствующих записей и штатные технические ошибки для остального. Подключение и логи исключают сырые строки, SQL diagnostics, DSN и секреты из ответов и журналов. NULL title обрабатывается как пустой. CSV и PostgreSQL используют общий разбор: trim внешних пробелов как в CSV loader, первое слово для ShortName, остальные для LastName, одно слово в UnstructuredName, без эвристики отчества. CSV хранит int64-ключ, проверяет числовые дубликаты и сохраняет существующую обработку невалидных строк и неизменные demo fixtures.
4. **Конфигурация.** В composition root SITE_SOURCE принимает csv (по умолчанию) или postgres. CSV требует SITE_PATH, PostgreSQL требует отдельные SITE_DB_HOST, SITE_DB_PORT, SITE_DB_USER, SITE_DB_PASSWORD, SITE_DB_NAME и явный SITE_DB_SSLMODE. CRM_PATH и собственные DB_* обязательны как прежде. Пул сайта создаётся и проверяется только для postgres, закрывается при завершении и на ошибках инициализации. Невалидный режим или недоступность выбранного источника останавливает запуск. Для внешнего соединения используются минимальные права чтения. Мигратор работает с собственной БД. Текущий /healthz проверяет собственную БД, ошибки чтения сайта обрабатываются в соответствующих запросах.

## Risks / Trade-offs

- Текстовые варианты одного ключа могут конфликтовать после конвертации → проверять числовую уникальность до изменения типа.
- Изменение типа переписывает таблицу и блокирует доступ → выполнить в окне обслуживания с остановленными писателями, резервной копией и проверкой восстановления. При провале завершить транзакцию без изменения схемы и строк.
- Смена источника может повторно использовать тот же числовой ID у другой записи → CSV demo и PostgreSQL-режим используют раздельные наборы данных БД связей, если принадлежность существующих связей выбранному набору не установлена. Автоматического переноса между наборами нет.

## Migration Plan

1. Новая Goose-миграция собственной БД в одной транзакции. Взять ACCESS EXCLUSIVE на client_links перед проверками. Проверить все строки на десятичный целочисленный формат после согласованного SQL trim ASCII whitespace, затем проверить BIGINT cast с обнаружением переполнения. Проверки идут отдельными шагами, чтобы оптимизатор не мог выполнить cast до проверки формата. Агрегировать нормализованные int64 для поиска коллизий. При ошибке прервать миграцию с безопасной диагностикой без исходных ID.
2. После проверок снять только текстовый CHECK chk_client_links_site_id_not_empty и сменить тип через ALTER COLUMN TYPE BIGINT USING то же выражение приведения. Сохранить NOT NULL, именованные UNIQUE обоих ключей, PK, audit CHECK, данные и defaults. Не добавлять внешний FK.
3. После Up запустить совместимую версию приложения. При откате остановить приложение, выполнить транзакционный Down с BIGINT::TEXT и восстановить исходный CHECK, запустить предыдущую версию. Down сохраняет числовые значения и аудит, но форматирует ключи канонически и не восстанавливает ведущие нули, знак плюс и пробелы. Для побайтового восстановления исходных строк использовать резервную копию, учитывая записи после обновления. Старые миграции остаются историческими.
