# Design

## Context

- `backend/cmd/server/main.go` собирает CSV CRM, выбранный SiteReader и PostgreSQL-репозиторий связей. Оба PostgreSQL-адаптера держат конкретный `*pgxpool.Pool`. `db.NewPool` проверяет PostgreSQL при запуске. `/healthz` проверяет пул связей.
- SiteReader выполняет единственный запрос по ключу к `public.children` с чтением `id`, `title` и преобразованного `birthday`. В репозитории связей операции Create, List и LookupBySourceIDs используют неуточнённое имя `client_links`. Три текущие миграции используют то же имя и применяются отдельным сервисом `migrate` в локальном Compose. Финальный backend image сейчас содержит только бинарник приложения.
- Мотивация и границы Stage 3 зафиксированы в [proposal.md](proposal.md).

## Goals / Non-Goals

- Держать SSH, настройки пулов и Goose в platform, порядок и владение ресурсами в composition root. Существующие порты, адаптеры, SQL и HTTP-контракт сохраняются.
- Восстанавливать транспорт и PostgreSQL-сессии без переподключения бизнес-компонентов к новому объекту пула. Повторы SQL и перенос данных из ранее созданных схем выходят за рамки транспорта.

## Domain Concepts

Новых доменных понятий нет. SITE остаётся внешним источником записи сайта. Для `timestamp without time zone` текущий запрос интерпретирует значение как UTC и возвращает календарную дату Europe/Moscow. OD — техническое имя собственной PostgreSQL базы. Связь двух идентификаторов, её уникальность и атомарный аудит сохраняют существующую семантику.

## Decisions

### Выбор транспорта и параметры подключения

В `internal/platform/config` ввести `DB_TRANSPORT` с default `direct` и сохранить default `SITE_SOURCE=csv`. Допустимы три сочетания:

| DB_TRANSPORT | SITE_SOURCE | SITE | OD |
| --- | --- | --- | --- |
| direct | csv | CSV из SITE_PATH | Прямое подключение по DB_* |
| direct | postgres | Прямое подключение по SITE_DB_* | Прямое подключение по DB_* |
| ssh | postgres | Туннель SITE | Туннель OD |

Отклонять неизвестное значение любого переключателя и сочетание `ssh + csv` до подключения к источникам. При `ssh` пропущенный `SITE_SOURCE` получает default `csv` и также приводит к ошибке. Один переключатель выбирает общий режим транспорта для обеих БД, а настройки и жизненный цикл SITE и OD независимы. Production Compose явно задаёт `DB_TRANSPORT=ssh` и `SITE_SOURCE=postgres`. `CRM_PATH` обязателен во всех режимах.

| Назначение | SITE | OD |
| --- | --- | --- |
| SSH host и user | SITE_SSH_HOST, SITE_SSH_USER | OD_SSH_HOST, OD_SSH_USER |
| SSH аутентификация | SITE_SSH_PASSWORD, метод password | OD_SSH_KEY, файл ключа без passphrase, метод publickey |
| Цель проброса на SSH-сервере | SITE_HOST=localhost | OD_HOST=localhost |
| PostgreSQL-аутентификация | SITE_NAME, SITE_USER, SITE_PASSWORD | OD_NAME, OD_USER, OD_PASSWORD |

Хосты SSH задаются именем или IP без порта. Использовать TCP 22 для SSH и TCP 5432 для PostgreSQL через `net.JoinHostPort`. Порты локальных слушателей назначает ОС. В режиме SSH с `sslmode=disable` требовать `SITE_HOST=localhost` и `OD_HOST=localhost`. Иное значение отклонять при проверке конфигурации. Каждый SSH-сервер должен разрешать `localhost` только в собственный loopback, где PostgreSQL слушает TCP 5432. Команда деплоя обеспечивает такое разрешение имени и правила `pg_hba.conf`, допускающие локальное TCP-подключение без SSL для соответствующих пользователей и БД. SSH шифрует участок до проверенного SSH-сервера. Direct сохраняет действующий SSL-режим.

### SSH-сессии и проверка доверия

Один компонент в `internal/platform/sshtunnel`, два экземпляра. Каждый держит TCP listener на `127.0.0.1:0` на весь срок жизни компонента. Подключение PostgreSQL к локальному сокету открывает через текущую SSH-сессию канал `direct-tcpip` к своему удалённому `HOST:5432`. Двунаправленное копирование учитывает half-close и освобождает оба конца по завершении или отмене. Список активных сокетов принадлежит открывшей их SSH-сессии. Listener и фиксированный адрес позволяют переиспользовать обычный TCP-клиент pgx с работающими дедлайнами. Прямой `DialFunc` на SSH-канале потребовал бы адаптации, так как `x/crypto/ssh` возвращает ошибку для SetDeadline на канале.

До первоначального подключения проверить обязательный `SSH_KNOWN_HOSTS_PATH`, читаемость файла и наличие записей с доверенными ключами. Пробелы и комментарии сами по себе не образуют доверие. Использовать OpenSSH-формат и `knownhosts.New`, проверяя весь файл, в том числе ошибочные строки после валидной. Проверка формата дополнительно сверяет заявленный тип ключа с типом декодированного ключа, поскольку библиотечный парсер игнорирует это поле. При каждой попытке открыть SSH загрузить и проверить файл заново и передать строгий callback в `ssh.NewClientConn` с настроенным SSH-адресом, а не адресом локального проброса. Файлы должны быть стабильны на время чтения. Ключ, пароль и данные файла исключены из логов. OD разбирает приватный ключ через `ssh.ParsePrivateKey` и отклоняет зашифрованный или некорректный ключ. Каждая сессия предлагает только свой метод SSH-аутентификации.

Исходящий TCP connect и SSH-handshake занимают до 5 секунд суммарно. Использовать контекст для dial, временный deadline на сыром TCP и закрытие сокета при отмене handshake. После успеха снять deadline. Разрыв отслеживать через `ssh.Client.Wait`. Для обнаружения зависания каждые 15 секунд отправлять один глобальный `SendRequest("keepalive@openssh.com", true, nil)` на сессию с внешним таймаутом 5 секунд на отправку и ответ. Ответ с `err == nil` подтверждает живой транспорт при любом значении `ok`.

Открывать канал через `ssh.Client.Dial` с внешним лимитом 5 секунд. `DialContext` ограничивает ожидание вызывающего кода, а внутреннее открытие канала может продолжаться. Таймаут keepalive или открытия канала и ошибка транспорта запускают один путь снятия соответствующей сессии с обслуживания. Закрыть её сырой TCP и локальные сокеты, чтобы разблокировать `Wait`, `SendRequest`, открытие каналов и копирование. Операции принадлежат конкретной сессии и учитываются до завершения. Перед публикацией замены и при остановке дождаться их завершения вне блокировки. Передача результата не должна блокировать операцию после ухода ожидающего кода. Поздний канал закрывается, а запоздалое событие старой сессии не влияет на новую. Явный отказ открыть канал закрывает только конкретный проброс. Ограничить число одновременных пробросов на туннель до 32 с учётом фоновых и отменяющих подключений pgx. Лишний локальный сокет сразу закрывается.

### Восстановление пулов

Один supervisor на туннель сериализует потерю сессии и публикацию новой. При обрыве под блокировкой снять старую сессию с обслуживания и забрать список её локальных сокетов. Затем закрыть старый TCP и эти сокеты и вызвать `Reset()` только у соответствующего `pgxpool.Pool`. Supervisor публикует новую SSH-сессию после Reset. При accept сокет регистрируется под той же блокировкой до открытия канала. Открытие канала и копирование идут вне блокировки. Поздний результат открытия канала от старой сессии закрывается. Во время паузы listener сразу закрывает принятые сокеты. Пулы связываются с туннелями перед публикацией первых SSH-сессий. Мониторинг обрывов активен с первой сессии. Во время startup её потеря отменяет запуск. После успешного startup обрыв запускает reconnect соответствующего туннеля.

`pgxpool.Reset()` в pgx v5.12.0 вызывает сброс puddle v2.2.3. Он сразу изымает свободные ресурсы с асинхронным закрытием и уничтожает выданные ресурсы прежнего поколения при возврате. Уже выданные соединения теряют возможность I/O при закрытии сокетов старой SSH-сессии. Фоновый `CreateResource` может завершиться после Reset и поместить результат в idle. Reset сам по себе не защищает от выдачи такого ресурса.

Каждой опубликованной SSH-сессии присваивать уникальный для туннеля идентификатор. В туннельном `ConnConfig.DialFunc` считывать его под блокировкой перед открытием обычного loopback TCP и сохранять в обёртке `net.Conn`, делегирующей дедлайны. Без опубликованной сессии завершать dial ошибкой. Идентификатор в обёртке остаётся прежним, даже если `accept` пришёлся уже на следующую сессию. Это допускает отбрасывание поздно открытого соединения, но исключает выдачу старого под новым идентификатором. `pgxpool.Config.PrepareConn` получает обёртку через `conn.PgConn().Conn()` и под той же блокировкой сверяет идентификатор с активной сессией. При несовпадении вернуть `false, nil` для уничтожения ресурса и повторной выдачи из пула. Если активной сессии нет, вернуть `false` и ошибку недоступности. Если сессия пропала сразу после проверки, этот запрос может завершиться ошибкой при закрытии её сокета.

После публикации новой сессии тот же пул создаёт физические соединения на прежнем loopback-адресе при Acquire и при фоновом пополнении до минимума. Критерий восстановления — успешный SQL через прежние адаптеры и только новые backend PID среди успешно выданных соединений. В контролируемом тесте задержать фоновый конструктор после PostgreSQL startup старой сессии, вызвать обрыв и Reset, опубликовать новую сессию, затем отпустить конструктор. В этом тесте отключить автоматический `Ping` при выдаче через тестовую настройку `ShouldPing`, чтобы проверить срабатывание `PrepareConn`. Устаревший ресурс отклоняется до выдачи, а второй пул продолжает работать.

Между неуспешными попытками использовать паузы 1, 2, 4, 8, 16 и далее 30 секунд, с отменяемым ожиданием. Сбросить накопленную паузу после успешного ответа keepalive от восстановленной сессии. Остальное приложение и второй туннель продолжают работу. Для туннельных пулов задать connect timeout 5 секунд и использовать существующие размеры пулов. Сбой запроса возвращается через текущие обработчики ошибок. Транспорт не повторяет SQL, поскольку при обрыве ответ на запись может потеряться после фиксации транзакции.

### Схема OD и Goose

Для каждого физического production OD соединения передавать `search_path=apps` в `pgx.ConnConfig.RuntimeParams`. Это действует с первого SQL-запроса, включая новые соединения после сброса пула. Пересоздавать схему или менять серверные настройки ролей для этого не требуется. Перед миграциями проверить `current_schema() = 'apps'`, `USAGE` и `CREATE`. Не добавлять `public` в search_path. Неявный `pg_catalog` продолжает предоставлять PostgreSQL 16 встроенные функции, включая `gen_random_uuid()`, используемую первой миграцией.

Использовать в процессе backend `pressly/goose/v3` v3.27.1, `goose.NewProvider` с PostgreSQL dialect и `WithTableName("apps.goose_db_version")`. В исходниках диалекта квалифицированное имя передаётся в SQL, а проверка существования разделяет схему и имя таблицы. `stdlib.OpenDBFromPool(odPool)` даёт Goose тот же OD-пул и те же параметры каждой физической сессии. Для пересекающихся запусков включить PostgreSQL session locker Goose с advisory lock. `Provider.Up` вызывает `HasPending` до взятия блокировки, поэтому конкурентную инициализацию таблицы версий обрабатывают встроенные повторы Goose. Под блокировкой Goose повторно читает список версий и применяет ожидающие миграции. Compose запускает один backend. Закрыть SQL-обёртку после `Provider.Up` и продолжить использовать OD-пул в LinkRepo. Goose v3.27.1 требует Go 1.25.7 и объявляет pgx v5.9.2 и x/crypto v0.50.0. При Go 1.26.1 ожидаемый граф по Minimal Version Selection включает Goose v3.27.1, pgx v5.12.0, puddle v2.2.3 и x/crypto v0.50.0 вместо текущей v0.48.0. Проверить выбранные версии после добавления Goose при Apply.

Встроить существующие SQL-файлы через `go:embed *.sql` в Go-пакете рядом с ними в `backend/migrations`. Backend image уже собирает Go-бинарник из этого контекста. Встраивание даёт Goose тот же набор SQL, который видит локальный контейнер через mount, и устраняет зависимость от cwd или дополнительного копирования миграций в финальный слой. Старые SQL и локальный Goose не требуют правок.

### Порядок запуска и остановки

Production проверяет конфигурацию, читает CRM CSV, создаёт два туннеля и связанных с ними пула. До привязки HTTP-порта выполняет обе проверки PostgreSQL, проверку схемы OD и `Goose Up`. После Up повторно проверяет оба пула, затем переводит supervisors в режим автоматического восстановления и запускает HTTP. Лимит инициализации подключений — 30 секунд, лимит Goose с блокировкой — 2 минуты, лимит финальной проверки обоих пулов — 5 секунд. При отмене startup, потере любой из первых SSH-сессий или истечении срока Goose закрыть пробросы, чтобы разблокировать PostgreSQL I/O, в том числе попытку Goose снять advisory lock с контекстом без отмены. При ошибке startup освободить открытые ресурсы и завершить запуск. Следующий старт читает журнал Goose и продолжает с неприменённых версий. Runtime reconnect не запускает миграции повторно.

`/healthz` сохраняет проверку пула связей и текущий контракт. После открытия HTTP недоступность SITE возвращает штатные ошибки только в сценариях, которым нужен сайт. Для остановки держать отдельный отменяемый lifetime соединений, чтобы сигнал не оборвал transport раньше HTTP drain. Сначала остановить приём и дать HTTP до 10 секунд на завершение. При истечении срока отменить контексты запросов и принудительно закрыть HTTP. Затем прекратить попытки reconnect, закрыть слушатели и сокеты SSH с пробросами, дождаться завершения supervisor, после чего закрыть пулы. Закрытие транспорта перед `Pool.Close` разблокирует оставшийся I/O. Для недостроенного startup действует тот же порядок освобождения доступных ресурсов. Compose выделяет 20 секунд для SIGTERM.

### Production Compose

Использовать самостоятельный `docker-compose.prod.yml` с отдельным Compose project name, чтобы он не сливался с локальным стеком. Оставить имена `backend` и `frontend` для nginx `backend:8080`. Frontend ждёт существующую HTTP healthcheck с `start_period: 165s`, учитывающим инициализацию и миграции. Опубликовать только frontend на `127.0.0.1` с `FRONTEND_PORT` по умолчанию 3000. Backend может устанавливать исходящие соединения по обычной сети Compose. Существующий frontend image и nginx-конфиг переиспользуются.

Среде запуска передаётся runtime env с production-параметрами. Compose явно передаёт нужные имена переменных backend. Для файлов использовать long-syntax bind mounts с `read_only: true` и `create_host_path: false`. В Compose абсолютные хостовые пути из `OD_SSH_KEY`, `SSH_KNOWN_HOSTS_PATH` и `CRM_PATH` отображаются на фиксированные пути контейнера. Значения одноимённых переменных backend указывают на эти пути контейнера. Проверить открытие файлов по заданным контейнерным путям от имени пользователя `app`. Read-only mount ограничивает запись, а чтение зависит от прав файлов. Ограничить `backend/.dockerignore` списком путей, требуемых для сборки, и исключить из него файлы окружения. Production-файлы передаются из-за пределов обоих build contexts. На сгенерированных тестовых файлах проверить исключение из обоих эффективных build contexts и отсутствие файлов в обоих итоговых образах без runtime mounts. Значения runtime env не передаются в Dockerfile и build args. В отдельном документе Stage 3 описать переменные, mounts и запуск, включая локальную привязку frontend и условие доверенного окружения.

## Risks / Trade-offs

- Разрыв после фиксации записи и до ответа оставляет результат запроса неопределённым для клиента. Приложение сохраняет текущие ошибки и проверку состояния и уникальности при новом явном запросе.
- Рабочая SSH-сессия при недоступном PostgreSQL отличается от потери SSH. Неудачный проброс не выходит за пределы этого подключения. Новый Acquire сможет открыть подключение после возвращения PostgreSQL.
- Одинаковые имена в `apps` и `public` проверяются интеграционно для runtime и Goose. Тесты должны сравнивать состояние обеих схем, иначе успешный запрос сам по себе не подтверждает нужную схему.

## Migration Plan

1. Развернуть production Compose с подтверждёнными параметрами, существующей схемой `apps` и требуемым доступом OD_USER, после Verify на синтетическом стеке. В целевой схеме либо ещё нет объектов приложения, либо их происхождение подтверждает существующая история тех же Goose-миграций. При неожиданной структуре Goose может завершить запуск ошибкой. Перенос данных из `public` выполняется отдельным согласованным изменением при подтверждённой необходимости.
2. При проблеме остановить production-стек и исправить настройки или восстановить совместимый образ. Применённые Goose-версии сохраняются. Stage 3 автоматически выполняет только Up. Локальное окружение продолжает запускаться через свой Compose.
