# Spec Delta

## Purpose

Обеспечить production-доступ приложения к двум удалённым PostgreSQL, восстановление при обрыве SSH и применение миграций в выделенной схеме OD.

## ADDED Requirements

### Requirement: Независимые подключения SITE и OD

Production backend SHALL подключать SITE и OD через отдельные SSH-сессии с независимыми SSH- и PostgreSQL-учётными данными. SSH SHALL использовать порт 22. При `sslmode=disable` цели PostgreSQL SHALL быть loopback соответствующих SSH-серверов на порту 5432.

#### Scenario: SITE использует пароль

- **WHEN** backend настроен для production и подключается к SITE PostgreSQL 10.23
- **THEN** SITE использует SITE_SSH_HOST, SITE_SSH_USER и SITE_SSH_PASSWORD для SSH и SITE_HOST, SITE_NAME, SITE_USER и SITE_PASSWORD для PostgreSQL; SITE_USER работает с доступом только на чтение

#### Scenario: OD использует ключ

- **WHEN** backend настроен для production и подключается к OD PostgreSQL 16.15
- **THEN** OD использует OD_SSH_HOST, OD_SSH_USER и файл незашифрованного ключа OD_SSH_KEY для SSH и OD_HOST, OD_NAME, OD_USER и OD_PASSWORD для PostgreSQL; runtime и Goose используют одного OD_USER

#### Scenario: Недопустимая PostgreSQL-цель

- **WHEN** в SSH-режиме SITE_HOST или OD_HOST отличается от localhost
- **THEN** backend отклоняет конфигурацию до подключения к источникам

#### Scenario: Локальная цель на SSH-сервере

- **WHEN** команда деплоя настроила на каждом SSH-сервере разрешение localhost в loopback и разрешила соответствующее локальное TCP-подключение без SSL на внешней PostgreSQL
- **THEN** backend использует SITE_HOST=localhost и OD_HOST=localhost и подключается к каждой БД через свой SSH-туннель

### Requirement: Интеграционная проверка SITE на PostgreSQL 10.23

PostgreSQL 10.23 — фиксированная версия SITE вне официальной матрицы pgx v5.12.0. Stage 3 SHALL пройти интеграционную проверку именно на синтетической PostgreSQL 10.23. Проверка подтверждает только используемый сценарий. Её провал блокирует завершение Stage 3 до отдельного решения.

#### Scenario: Проверка SITE на PostgreSQL 10.23

- **WHEN** SiteReader подключается через SSH к синтетической PostgreSQL ровно 10.23 и читает записи с заполненным и NULL `birthday`
- **THEN** подключение успешно, `id`, `title` и `birthday` корректно читаются, а NULL `birthday` возвращается как отсутствующая дата

### Requirement: Строгая проверка ключей SSH-серверов

Каждое SSH-подключение SHALL проверять ключ сервера по доверенному файлу SSH_KNOWN_HOSTS_PATH. Backend SHALL отклонять подключение при отсутствующем, нечитаемом, пустом или некорректном файле, неизвестном сервере или несовпадении ключа, без интерактивного подтверждения и автоматического принятия ключа.

#### Scenario: Два доверенных сервера

- **WHEN** файл содержит доверенные ключи SITE и OD и каждый сервер предъявляет свой ключ
- **THEN** обе SSH-сессии проходят проверку независимо

#### Scenario: Файл отсутствует или недействителен

- **WHEN** путь отсутствует, файл недоступен, содержит только комментарии или включает некорректную запись
- **THEN** production backend отклоняет конфигурацию до начала обслуживания HTTP

#### Scenario: Ключ изменился при восстановлении

- **WHEN** при переподключении сервер предъявляет неизвестный, отозванный или несовпадающий ключ
- **THEN** этот туннель остаётся недоступным, а второй продолжает работу

### Requirement: Восстановление PostgreSQL после потери SSH

Backend SHALL автоматически восстанавливать потерянную SSH-сессию с exponential backoff и верхним пределом интервала. Backend SHALL выводить из обращения PostgreSQL-соединения потерянной сессии и обслуживать новые запросы через восстановленное подключение без перезапуска процесса. Потеря одного туннеля SHALL сохранять работоспособность второго.

#### Scenario: Обрыв или зависание одного транспорта

- **WHEN** после успешного запуска прекращается передача по SITE либо OD SSH
- **THEN** запросы через пострадавшую сессию завершаются ошибкой, а запросы, которым нужна только исправная БД, продолжают выполняться

#### Scenario: Нет ответа на SSH-запрос

- **WHEN** сессия перестаёт отвечать на keepalive или открытие канала
- **THEN** по истечении таймаута backend снимает с обслуживания эту сессию, закрывает её транспорт и пробросы и завершает принадлежавшие ей SSH-операции

#### Scenario: Возвращение доступности

- **WHEN** SSH-сервер с доверенным ключом и его PostgreSQL снова доступны
- **THEN** существующие адаптеры успешно обслуживают новые запросы через новые PostgreSQL-соединения, включая случай, когда в пуле были свободные и занятые соединения от потерянной сессии

#### Scenario: Фоновое пополнение одновременно со сбросом

- **WHEN** фоновое создание соединения через прежнюю SSH-сессию завершается после обрыва, сброса пула и публикации новой сессии
- **THEN** пул отбрасывает устаревшее соединение до выдачи, прежний адаптер работает через новую сессию, а второй пул продолжает обслуживать запросы

### Requirement: Схема приложения в OD

Production runtime и Goose SHALL использовать существующую схему apps для таблиц приложения, включая client_links и таблицу версий Goose. Схема SHALL быть фиксированной. Отсутствие схемы или необходимых прав SHALL прерывать запуск. Goose SHALL работать только через OD.

#### Scenario: Одноимённые таблицы в public

- **WHEN** у OD в public уже существуют одноимённые таблицы
- **THEN** Goose применяет версии в apps, а чтение и запись связей обращаются к apps, оставляя объекты и данные public без изменений

#### Scenario: Схема недоступна

- **WHEN** apps отсутствует или OD_USER не может использовать её либо выполнить необходимые операции
- **THEN** backend завершает запуск с ошибкой до обслуживания HTTP, без перехода в public

### Requirement: Готовность и завершение работы backend

Production backend SHALL принимать HTTP-запросы после успешных проверок обоих PostgreSQL-подключений и применения Goose Up из поставляемых миграций. Старт при ошибке подключения или миграций SHALL завершаться без обслуживания HTTP. Штатная остановка SHALL освобождать HTTP server, пулы, SSH-сессии и слушатели.

#### Scenario: Ожидание миграций

- **WHEN** обе БД отвечают, а Goose ещё применяет миграции через OD
- **THEN** HTTP-порт backend ещё не принимает запросы

#### Scenario: Ошибка при частично завершённом запуске

- **WHEN** один туннель уже открыт, а второе подключение или Goose завершается ошибкой
- **THEN** backend освобождает открытые ресурсы и завершает процесс с ошибкой

#### Scenario: Остановка во время переподключения

- **WHEN** backend получает SIGTERM при активных соединениях или во время reconnect backoff
- **THEN** HTTP прекращает приём, новые SSH-попытки отменяются при закрытии подключений, а все ресурсы освобождаются за ограниченное время
